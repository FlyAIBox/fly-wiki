# 视觉创作成品：开放式设计评审叠加合同

> 只在 `image`，或视觉表达承载信息 / 用户要求专业、可发布、可演示的 `document` 目标中读取本页。不要为 web、app、agent/model、skill/cli 或纯文字内容评测加载本页。

## 目录

1. 双轨与资产形态
2. Reviewer 与 packet 隔离

## 1. 双轨与资产形态

视觉创作成品必须同时保留两条互相隔离的证据轨：

1. **使用轨**：目标用户带着自己的事来理解、决定、转手使用，产生行为证据。
2. **开放式设计评审轨**：没参与创作的专业子代理公开以 reviewer 身份，从整体到局部自由判断结构、叙事、视觉系统与发布完成度。

两轨不能互相冒充。用户办成了事不证明设计已达到发布标准；专业判断也不能写成“用户已经受阻”。每轮有新版本时，两轨都要使用干净上下文。

在公共协议之上增加这些资产字段：

- `target.json` 写 `visual_creative: true`；PPT 仍是 `document`，另记目标比例、观看尺寸和播放顺序。
- 设计评审 scenario 使用合法的 `kind: "evaluation_probe"` 与 `open-design-review` tag。`goal` 写受众、用途和交付决定；`closure` 要求独立诊断、保留项、优先级和替代方向，不写疑似缺陷或理想答案。
- `case-index.json` 的本地 `track` 写 `design_review`；普通人物为 `task_user`。只有 kind、tag、track 三项同时成立才算设计评审，名字中出现 review 不算。
- Methodology 同时包含两轨，并保留一个真正开放的分析问题，不能只问上轮修复项是否通过。

评审 case 的 `succeeded` 只表示评审交付完成，不表示作品通过。两轨混跑时不得用总 `completion_rate` 代表成品质量；需要数字就分轨报告或拆 run。

## 2. Reviewer 与 packet 隔离

按目标选择真实专长：信息图/架构图看信息设计与技术传播；PPT 看演示叙事、版式和舞台可读性；品牌图看视觉系统与 art direction。至少一个 reviewer 必须与作者隔离，主代理自评不能充数；复杂、高风险目标可按未决问题增加互补专长。

Reviewer packet 只含：

- 最终渲染成品与真实观看尺寸；多页成品含整套缩略总览、逐页图和顺序；
- 目标受众、使用场合和沟通目标；
- 不可改的事实、品牌、格式和无障碍约束。

不要给作者解释、生成源码、候选身份、历史 feedback、既有分数、预想缺陷、上轮修改或准备采用的方案。可以列出常见观察面，但不能给待找问题清单或固定答案。

单候选 reviewer 只能看到一个中性命名版本。比较 reviewer 可以看到全部匿名候选，但顺序必须随机化并留档，且仍不知道原版、作者偏好或既定赢家。

## 3. 开放评审 prompt

在公共 trace 与执行循环合同前加入：

> 你是与作者隔离的专业设计评审者。只读取 packet 中的最终渲染成品、目标受众/用途、真实观看环境与不可改约束；不要读取或猜测生成源码、作者解释、候选身份、历史 feedback、既有分数或准备采用的方案。从整体到局部做一次开放式设计评审：先独立说出第一眼的主次、叙事与最该保住的强项，再自由判断什么限制了设计上限。不要只打分或照 checklist 找问题；可以讨论信息架构、故事线、构图、层级、字体、色彩、对比、节奏、一致性、可访问性和制作完成度，也主动寻找这些词没有覆盖的问题。每个关键判断回指实际画面，说明影响、结构级/系统级/元素级、优先级与可执行方向；若当前前提限制上限，提出至少一个说清换掉什么前提的替代方向。没有实质问题时如实给零 finding，不为凑数挑错。不要编辑成品。

Outcome 用普通文本收束 `Verdict / Preserve / Findings / Alternate directions / Unknowns`。每个 actionable finding 在主代理验收 trace 后获得稳定 source ID。

## 4. 画面证据与多候选

- 每个关键 finding 必须回指 `case/step/shot + 页码/slide/画面区域`，说明可见事实、对目标受众的影响、范围、优先级、方向和未知边界。
- 图片先在真实投放尺寸判断整体层级和效果，再按需要放大；不能只找像素瑕疵。
- PPT 先看整套缩略图判断结构、节奏、重复与转场，再按目标比例查看逐页渲染。缩略图不能是唯一证据；超过 10 页时分多个 step，遵守单步 `shots` ≤10。
- 开放评审通常 5–10 步，长 deck 按整套结构与代表页组织证据，不逐页凑步数。
- 多候选先让不同 reviewer 各只见一个匿名候选，保住无比较锚的独立首读；再派至少一个全新比较 reviewer，看随机顺序的全部候选，先逐版独立评再横向比较。

零 finding 合法，但仍须给整体 verdict、必须保住的强项和未知边界；禁止为显得认真而硬造缺陷。

## 5. Feedback 与 Loop 叠加

`feedback.md` 另设 `## 开放式设计评审`，与用户行为证据分栏。每个判断标明是用户直接观察、专业判断、合理推断还是未验证；专业判断不能伪装成用户失败，使用轨成功也不能抹掉设计 finding。

获得修改授权并已加载通用 Loop 合同时，再叠加：

- 每个可执行设计 finding 都进入处置账；高优结构/叙事前提否决或具体替代方向，默认物化为隔离生成的综合/另起候选对跑。若不采用，只能以可反驳证据 `rejected`；用户暂停可以 `deferred`，但必须 `converged: false`。
- 首轮不能只报一个赢家。落选候选和评审意见的可借项逐条入账并嫁接；出现高优结构发现或具体替代前提时物化综合候选，不为凑数强造第四版。
- 每个可计入收敛的视觉轮都必须派没见旧稿、diff 与历史 feedback 的新 reviewer，从整体重新打开问题；不能改造成旧 finding 验收员。
- 设计 case 的 `succeeded` 不等于作品通过。声称视觉质量充分完成，至少一名专业 reviewer 只见最终版；结论跨多种专长时再补相应独立视角。
- 只做微调且评审没有从整体重新打开设计问题，或缺开放评审 / 评审退化成 checklist 的轮次，不计入连续收敛轮。若新 reviewer 全局重审并以画面证据明确没有结构/系统级高优问题，微调轮才可计数。

视觉目标只有在通用收敛条件之外，再满足连续计数轮均含新开放 reviewer、没有未解决高优设计项时，才能写 `converged: true`。

## 6. 收尾检查

- 使用轨与设计评审轨都存在，角色、packet 和证据分开。
- Reviewer 与作者隔离；kind、tag、track 合法，没有新增伪枚举。
- 每个关键 finding 有真实画面、页/slide/区域和影响依据。
- PPT 已看整套顺序和逐页真实渲染；图片先在真实尺寸判断整体。
- 多候选保留独立首读与匿名随机比较。
- Loop 的设计 finding 无静默丢项，高优项未被 deferred 后伪装成收敛。
