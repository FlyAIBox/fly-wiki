# 人与事：把虚拟用户写成一个 agent

一个仿真用户不是一段角色设定，它自己就是个 agent：它得在没人递台词的情况下，看着一个陌生界面自己决定下一步。它凭什么决定？凭**它想起了什么**。

所以这一页只讲一件事：怎么写出「想得起东西来」的人，和「值得他今天去办」的事。

写薄的代价不是不够精致，是**行为消失**。一个只有身份标签的人设，模型没有任何可调用的具体经验，只能退回它的先验——一个耐心、积极、什么都愿意再试一次的平均人。四个这样的人跑同一件事会给出四份几乎一样的 trace，看起来像四个视角，其实是一个。

---

## 1. 三层不是三个字段，是一套加载机制

`profile` / `skills` / `memory` 不是并列的三段简介。它们在引擎里以不同方式进入模型的上下文：

| 层 | 怎么进上下文 | 所以它该装什么 |
| --- | --- | --- |
| `profile` | **恒常驻**在 system prompt | 身份锚：跨场景稳定的取舍倾向。短，一直占着位置 |
| `skills` | 常驻**一行目录**（name + 首句钩子），正文按处境浮现 | 每项一个有壁垒的本事，首句自己站得住 |
| `memory.episodes` | 按当前处境**检索 top-k** 浮现 | 大量具体经历，各自带检索键 |

判据是 `skills` 正文 + `memory` 的总字数：不超过 1200 字全量常驻；超过就切**渐进模式**——system 里只留身份锚和技能目录，细节每步按处境现算浮现（`engine/agent/prompt.py`：`_RESIDENT_BUDGET=1200`、`_MEMORY_TOPK=6`、`_SKILL_TOPK=4`）。

这条机制反过来告诉你该怎么写：

- **厚不费钱。** 越过 1200 字之后，你写第 7 条还是第 20 条经历，单步注入量是一样的（只浮现最相关的 6 条）。**薄才是浪费**——没东西可召回，模型只能自己编。
- **profile 要短。** 它一直占着常驻位置，写进去的每一句都在跟真正有用的东西抢注意力。生平塞这里就更糟：它挤掉了位置，又不会在需要时被想起。
- **一条经历能不能被想起，取决于它写了什么词。** 详见 §4。

同一份资产在本地子代理仿真里也照这个层次交给它：packet 里的 episodes 是「你会自然想起的事」，不是待执行的清单。落库之后平台 L1 重跑同一个人，走的就是上面这套注入。

## 2. 倒着写：memory → skills → profile

先写 profile 的人，写出来的一定是 profile-only 的人。因为一旦先定了「资深危机公关顾问，理性、重数据」，后面的 memory 就变成给这句话补例子，skills 变成把这句话拆成条目——三段说的是同一件事，密度是假的。

倒过来：

1. **先攒经历。** 他这些年具体干了什么、用过什么、被什么坑过、哪次翻了车。这一步不写字，先攒素材（§3）。
2. **再抽本事。** 从这些经历里读出他真正的操作流：他反复做对的那几件事是怎么做到的。
3. **最后蒸出身份锚。** profile 是前两者的索引——把「这个人在陌生情境里会怎么取舍」压成几句。写到这一步你会发现 profile 很好写，因为它只是在总结你已经知道的人。

验收口诀：**memory 答「我经历过什么」，skills 答「我最会做什么、怎么做到」，profile 答「所以我在没经验的地方会怎么选」。** 同一个事实只在一层出现；发现重复，说明你在用叙述量冒充信息量。

## 3. 采集：密度的唯一来源

跳过这一步、直接让模型「生成一个资深工程师画像」，出来的一定是刻板印象。密度来自先把素材问出来。

**真人**（有公开记录的）：检索深度访谈、一手自述、关键决策时刻。围绕四件事找：底层思维模型、价值观锚点事件、真实时空坐标（年份/地点/项目名）、可引用的原话。八卦和琐事不要，除非那件琐事本身就是他决策模型的一部分。

**原型**（某类岗位/某类用户）：没有传记可查，密度来自沿维度逐项拷问，把一个岗位标签问成一个活人。下面这张清单就是「极客到什么程度」的答案——**每一项都要具名、带数字、带年份**，写不出具体名字说明你还没想清这个人。

| 维度 | 拷问 | 空 → 实 |
| --- | --- | --- |
| **工具履历** | 他手上真正用过什么？哪个版本、哪一年、在上面干成了什么？ | ~~熟悉前端工程化~~ → 2019 起吃 webpack 4，2022 团队换 Vite 3 是他主推的，理由是冷启动从 40s 到 2s |
| **产出履历** | 他做过什么东西？多大规模、什么结果？哪个是他的骄傲，哪个是伤口？ | ~~有丰富项目经验~~ → 主导过一个日活 3 万的内部工单系统，上线半年被砍，因为没人愿意从微信群搬过来 |
| **迁移史** | 他从什么换到什么？为什么换？被什么坑到弃用？ | ~~注重效率~~ → 用过 Notion 两年，因为 2000 条以后搜索变慢弃用，现在回到本地 Obsidian + git |
| **既有判断** | 他对同类东西已经有什么看法？为什么？ | ~~对新工具持开放态度~~ → 对「AI 帮你写测试」一律先怀疑：Copilot 生成的测试他抽查过一批，断言都在复述实现 |
| **动作链** | 他一天真实的动作序列：开什么、看什么、产出什么、在哪等人 | ~~每天处理大量数据~~ → 早上先看 Grafana 那三块板，然后翻夜里的告警群，中午前把值班交接贴发出去 |
| **协作姿态** | 他怎么写文档、怎么吵架、怎么说服人？向上向下各是什么样？ | ~~沟通能力强~~ → 不信口头结论，一律要求把数字贴进群；跟老板汇报只讲三条，剩下的写在链接里 |
| **失败模式** | 他最容易栽在哪？别人诟病他什么？他自己的盲区？ | ~~偶尔急躁~~ → 一旦某个方案是他提的，会不自觉忽略反面证据，团队里有人专门盯这个 |

**边界（这条边界比密度更重要）**：写「他对**别的**东西的既有判断」，绝不写「他对被测物的看法」。前者是人设——他为什么形成现在这套判断标准；后者是把结论提前塞进轨迹，整轮评测作废（`.claude/rules/eval-authoring.md`）。

写「被 Copilot 生成的测试骗过，从此抽查断言」是人设。写「他会挑剔我们这个功能不够准」是自证预言。

同一批人之间要**真的分叉**：把同一个处境摆到他们面前，取舍应该明显不同。都会「先看文档再动手」就是塌了，回去把迁移史和失败模式写开。

## 4. episodes 怎么写才会被想起

这是全页最容易做错、也最省不掉的一处。引擎按当前处境给每条经历打分，只浮现前几条：

```
score = |处境词 ∩ 经历词| / sqrt(经历词数)
处境 = scenario.goal + scenario.env + 上一步独白 + 当前观察
```

三条后果，都是硬的：

**一、`situation` 是检索键，不是编年史标题。** 用他**将会遇到的那个处境的词**，不是用「2023 年的一次技术选型」这种档案标题。他今天要评估一个命令行工具，那么「上次评估一个命令行工具要不要换掉现有流程时」就会被想起；「职业生涯第三次技术转型」不会——一个词都对不上。

**二、一条一事，写短。** 分母是 sqrt(词数)，长经历会稀释自己的分。一段三百字的完整故事往往输给一条二十字的无关小事。

**三、一旦有了 `episodes`，`memory.text` 就完全不进模型了。** 两个模式都一样（`_render_memory` 有 episodes 就只渲染召回结果，`_memory_units` 也只取 episodes）。所以别把重要背景留在 `text` 里等它生效——该进模型的东西全写成 episode，`text` 留空，或只当给人看的档案说明。只有一条 episode 都没写时，`text` 才会被整块注入（旧资产的兼容路径）。

对照（同一个人、同一件事）：

```jsonc
// 不会被想起：标题式、太长、没有处境词
{"situation": "职业生涯中的一次重要技术决策",
 "behavior": "在经过充分调研和团队讨论之后，我们最终决定采用一套新的工具链，这个过程涉及大量的评估工作……",
 "outcome": "积累了宝贵的经验"}

// 会被想起：处境词命中、一条一事、留下了判断
{"situation": "上次评估一个命令行工具要不要替掉现有流程",
 "behavior": "没看 README 的宣传语，直接拿手上一条真流水线跑，卡在密钥注入",
 "outcome": "从此评工具只认一条：能不能在我自己的真任务上跑通，跑不通就不看后面了"}
```

`behavior` 写他当时**真做了什么**（具名动作、具名工具），`outcome` 写**留下了什么判断**——outcome 是这条经历之所以还留在脑子里的原因，也是它影响今天行为的通路。

数量：够用就行，别凑。一个人身上真值得记住的具体经历，通常 6–14 条；写到第 15 条还全是新信息，那就继续写，反正只浮现最相关的几条。

## 5. skills 怎么写

**首句是目录钩子。** 渐进模式下 system 里只留 `name` + `text` 第一句的前 40 字，正文按需浮现。第一句要能单独立住——它是他自己在扫自己的目录时看到的东西。

**写机制，不写脚本。** `text` 说「我怎么做到、达到什么效果」，不是「遇到 X 我就做 Y」。后者是把行为写死，等于替他决定了下一步，评测就看不到真实选择了。

**2–8 项，宁缺毋滥。** 每项 60–110 字，彼此不重叠、都得有壁垒。凑数本身就是污染：为了达标塞进去的重叠项会挤占目录，让真正的本事更难被想起。

---

## 6. profile 怎么写

300–500 字，第一人称。只装三样：跨场景稳定的取舍倾向（遇到没经验的事第一反应是什么）、不随环境改变的性情、以及一道让他立体的裂缝（他自己知道的矛盾）。

不装：生平（去 memory）、能力清单（去 skills）、对被测物的看法（哪都不去）。

它一直常驻，所以每一句都要值得一直占着位置。

## 7. 密度预算与自检

| 段 | 预算 | 说明 |
| --- | --- | --- |
| `profile.text` | 300–500 字 | 常驻，超 700 就是在挤有用的东西 |
| `memory.episodes` | 6–14 条，每条 40–120 字 | 主力。短、具体、带处境词 |
| `memory.text` | 留空 | 有 episodes 时它根本不进模型；只在完全不写 episodes 的旧形态里才用 |
| `skills` | 2–8 项 × 60–110 字 | 首句能单独立住 |
| 合计 | 1500+ 字 | 越过 1200 字外挂预算即进渐进模式，这是**目标形态**不是超标 |

```bash
python3 scripts/check-cast.py persona.json scenario.json
python3 scripts/check-cast.py session/            # 整个 session 一次过
python3 scripts/check-cast.py persona.json --scenario scenario.json --target "MiroFish"
```

它报三类东西：形状/密度缺口、**这个人在这个场景下哪几条经历会真的浮现**（用引擎同一套打分算的）、以及人和事里有没有出现被测物的名字（自证预言）。

召回预览是最值得看的一项，用法是个短循环：看你**指望这次起作用的那几条**在不在前六。不在，就把它的 `situation` 改成他将会遇到的处境的词再看一次——这比继续加新经历有用得多。一条都进不了前六，说明这个人今天用不上他的过去，那要么换人，要么换场景。

## 8. scenario：一件真事的前因后果

persona 是谁，scenario 是他今天为什么会碰上这件事。它同时还是**召回查询**——写它用的词决定了哪些经历会被想起，所以用他世界里的词，别用抽象概括。

- **`goal`**：他想得到什么结果，**以及为什么是现在**。「想试试这个工具」不是目标；「明天要给团队定选型，今天得拿出一个能跑的证据」才是。
- **`env`**：他手上真带了什么——具体材料、时间预算、谁在等这个结果、他已经试过什么。这一段决定他愿意折腾几次就走。
- **`closure`**：可观察的成功证据，和他会**自然离开**的条件。放弃条件写不出来，说明这个人被写成了不会走的人，那就测不出流失。

不写操作步骤、不写疑似缺陷、不写正确答案，也不写「留意 X 好不好」——最后这条是最常见的污染：它把用户变成审稿人。

任务必须在**真实测试环境里办得成**：不要依赖测试工作区里并不存在的具名同事、历史讨论串或数据。persona 的 memory 里可以有虚构的旧同事（那是人设），但 scenario 的任务要用这个工作区里现有的人和东西措辞，否则虚拟人如实找不到、放弃，而评测会把这误读成产品办不成事。

---

## 9. 两条最常翻车的地方

**塌成 profile-only。** 症状：memory 是一句「持续背景」，skills 两条泛泛，episodes 空着。后果是四个人跑出一份 trace。补法不是把 profile 写长，是回到 §3 把素材问出来。

**把评测口径写进人和事。** 症状：persona 里写了他对被测物的态度，scenario 里写了「判断值不值得用」。后果是自证预言——你会得到你写进去的那个结论，而且看起来像是测出来的。人和事只写客观事实与自然处境，所有判断都从行为里**读出来**。
