# 评测装备:从项目抽取 Use,按需引入外部 Skill

评测的效率和深度取决于装备:**对内**把被测项目里已有的能力抽取成 Local Use,**对外**在能力缺口时调研并引入现成的 skill。两者都在组织 cases 阶段完成；只有决定使用非零 Local Use 后，才按 SKILL 路由加载 [local-use.md](local-use.md) 的字段合同。

## A. 从当前项目抽取 uses

被测目标在一个项目仓库里时,不要等子代理卡住才临时造 Use——先做一次**产品操作面盘点**,把评测用得上的能力成建制地抽出来。

**边界先立住(最高优先)**:

- 这里的 use 全部是**产品使用上的能力**——产品构建并运行起来之后,经它自身入口(产品 CLI、HTTP API、界面、导入导出等)能做的事。**项目运行/工程侧的能力不是 use**:构建、启动、跑测试、种子脚本、读仓库文件,这些属于评测装置的准备动作,归 preflight,不写进 `uses.local.json`,更不进 packet。
- **源码只用来「读懂产品怎么用」**:主代理读 README、API 文档、CLI 定义、路由/页面代码,目的只有一个——搞清产品对使用者暴露了哪些入口和能力,产出 use 的 contract。use 的 binding 一律打到**运行中的产品实例**(调它的 API、执行它的 CLI、操作它的界面),绝不绑定仓库脚本或源码函数。
- **模拟过程只见运行产物**:子代理能接触的只有构建/运行起来的产品(部署实例、装好的 CLI、打包产物)。仓库源码不在任何 case 的可见范围——除非被验证物本身就是代码或文档。

### 盘点顺序(主代理亲自做,10 分钟量级)

1. `README` / 用户文档 / 快速开始——产品自己声明的使用入口与前置条件;
2. CLI 的 `--help` 全树、HTTP API 文档(OpenAPI 等)——用户可编程入口全集;
3. Web / 移动端的页面与操作(必要时读路由、页面代码来确认有哪些界面能力);
4. 产品自带的账号体系、数据导入导出、状态查询/健康检查等对外可观察面。

盘点产出两份东西:**target.json 里的真实入口清单**(用户本来就该走的路,是被验证物,不包成 use),和**候选 use 清单**(评测用得上的产品周边能力)。

### 两类值得抽取的 use(按评测价值)

| 类别 | 例子 | 价值 |
|---|---|---|
| **基本操作的原子化**:把用户显然会做、但执行层容易绕圈子的机械操作包成可靠一步 | 「用测试账号登录并落到工作区」「把这份历史数据导入产品」「发一条消息」 | 步数与信号留给真正要验证的路径;执行摩擦不再被误读成用户放弃(那是最大的信号污染源) |
| **persona 现实的周边能力**:这个人现实中本来就有、经产品真实入口的手段 | 客服的「查账单」内部接口、运维可见的产品管理台 | 深度:用户能走到没有它就走不到的深路径 |

包哪些操作,判断标准只有一条为主:**它不在本次验证问题的焦点路径上**——验证问题若就是「新用户能不能自己完成登录」,登录就绝不能包;不是焦点、persona 显然会做、执行层又容易空转的,才值得包。包它是消除执行摩擦,不是替用户完成被验证的体验。

⚠️ **两个不叫 use 的东西别包进来**:① 核验用户办没办成,走界面看——trace 的观察与 done 闸要的本来就是页面状态、截图这类用户可见证据,不造 API 探针;主代理确需后端对照来清洗测试数据问题时,那是装置工具,记在 preflight / session 笔记,不进 `uses.local.json`,其结论不进产品分。② 拿查询「对照界面显示对不对」是 QA(通过/失败口径),不是评测,禁止。

环境预置与复位(起服务、灌种子数据、重置状态)是评测装置的事:能经产品自身入口做(如调产品 API 批量造数)就经产品入口做,只在 preflight 与 case 间复位时使用,不叫 use、不进 packet。

### 走一遍:从盘点到 `uses.local.json`

以一个假想的订阅制记账 SaaS 为例,盘点四步各看到什么、落成什么:

1. README 说「Web 应用 + REST API,`/api/docs` 有 OpenAPI」→ 入口清单记 Web UI(被验证物),API 记为候选面;
2. OpenAPI 里有 `POST /api/import`(导入历史账目)和 `POST /api/seed`(灌演示数据)→ 前者在「用户带着自己的历史数据来办事、导入本身不是验证焦点」的 case 里包成基本操作 use;后者是环境预置,归 preflight,不是 use;
3. 页面路由里有管理台 `/admin`(运维可见)→ 只有 persona 现实中就是运维/客服时才候选(周边能力),普通用户 case 不注入;
4. 健康检查 `GET /health` → preflight 用,不进 packet。

候选定下后,每个 use 落成 contract(能做什么、要什么参数)+ binding(打到**运行中实例**的真实调用)+ exposure(子代理看到的命令),字段全文与示例见 [local-use.md](local-use.md),本页不重复;落地前照下面的抽取纪律逐条过。

### 抽取纪律

- 每个抽出的能力写进 `uses.local.json`(contract + binding + exposure),binding 指向运行中的产品实例,preflight 在一次性状态副本上试跑成功后才可注入 case。
- **现实性红线不变**:只注入 persona 现实可用的能力,不能成为绕过被验证入口的后门。
- 「用户本来就该走的公开入口」不要包成 use——那正是要被验证的东西。
- 平台已有对应 use 资产且有真实可平台执行的实现时按 cli.md 引用;纯本地 binding 留在 session,不上传。
- **0 个是常态,数量由场景决定**:多数评测不需要任何 use;需要时,数量由场景路径上有多少个非焦点基本操作决定(协作类场景合理地会多),不设硬上限——纪律不在数字,在每个 use 都过三问:不在验证焦点路径上、persona 显然会做、执行层确实容易绕圈子。周边能力按 persona 现实持有逐个论证。超过一只手先自查:是不是把产品公开入口整个包成了 API 壳——那子代理就不是在用产品,是在调它的接口。

## B. 引入外部 skill

评测装置(不是 persona)缺某种能力时——录屏对比、批量造数、无障碍检查、性能采样、报告渲染、图像生成(图类候选出图,见 loop.md §2)——先找现成的 skill,不要立即降级收窄结论,也不要手搓一个劣质版。

### 流程

1. **写下能力缺口**:一句话说清缺什么、用在评测的哪一环(采证/预置/分析)。
2. **先查本地**:宿主已装的 skills / 插件里可能已有;有就直接用。
3. **网上调研**:按缺口关键词检索 skill 市场、GitHub、包仓库;比较候选的维护状态与适配面。
4. **装前审查(不可跳过)**:第三方 skill 是不可信代码——先读它的说明与脚本,确认没有越权动作(外传数据、动全局配置、要凭据);要凭据的一律不给真实凭据。
5. **隔离试跑**:装进主代理宿主后,先在与本次评测无关的样本上跑一次,确认行为符合声明。
6. **投入使用并留痕**:在 `session.json` 记录装了什么、版本/来源、用在哪一环;它产出的材料(录屏、报告)归入 evidence 或分析材料。

### 使用边界

- 外部 skill 默认是**主代理/评测装置的装备**:用于准备环境、采集证据、加工分析。
- 要把它交给子代理,必须过 persona 现实性判断:这个人现实中会有这个手段吗?会,才按 Local Use 的 exposure 方式注入;不会,就只留在装置侧。
- **绝不用外部 skill 替 persona 完成被验证的任务本身**——那是伪造用户成功。
- 装不到合适的 skill 时,回到既有姿势:降级做更窄验证并改写结论边界,或如实记 execution limitation。
