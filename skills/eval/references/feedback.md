# 证据综合、反馈与本地交付合同

> 只有综合已验真 traces、写 `feedback.md` 或交付本地 run 时读取本页。不要为了规划或执行提前加载；未通过验真的 trace 不得进入综合。

## 1. 先分证据类型

按验证问题读取所有有效 trace，区分：

- 直接观察到的行为与结果；
- 目标叠加合同允许的专业判断；
- 有证据支持的解释；
- 尚未验证的推断与未知；
- 装置限制；
- 成功路径的价值，以及办成但费劲、返工或绕路的成本。

按目标相关性、失败后果、证据强度与覆盖范围排序，不按出现次数投票。一个关键人物在关键路径上的失败可能比多个低影响摩擦更重要；反复返工不能归成“个人习惯”后静默丢弃。

## 2. `feedback.md` 结构

第一节固定为 `## TL;DR`，三到五条，每条一句、先结论后依据；第一条是整轮最重要判断，因为 viewer 用第一行非标题文字作为 run 摘要。随后依次写：

1. 对原验证问题的直接回答；
2. 外部行为证据；
3. 对当前工作的含义；
4. 产品新需求清单；
5. 未决事项与验证边界。

目标叠加合同可以增加专属章节。每个重要判断回指 case / step / evidence，并标注直接观察、专业判断、合理解释或未验证。不要用背景铺垫、方法复述或无结论数字占据 TL;DR。

## 3. 产品需求四件套

每条需求写成产品结果，不把实现方案伪装成需求：

```markdown
- **需求**：<哪类用户>在<什么处境>需要<得到什么结果>。
  **证据**：case/step/evidence 回指 + 一句实际发生了什么。
  **不满足的后果**：放弃、绕路、误解或回到旧工具等结果。
  **优先级**：高/中/低 + 关键路径、证据强度与覆盖范围依据。
```

例如“首次使用者需要不查外部资料就能完成 API key 配置并跑通第一条命令”是需求；“README 加一节配置说明”是实现方案。只有实现本身就是被测物，或用户已授权修改时，才另列实现建议。成功路径也要保留，避免改坏已有价值。

视觉成品同时按 `design-review.md` 分栏呈现用户行为与专业设计判断。已获修改授权时，再按 `loop.md` 为所有 actionable finding 建处置账；只评测时不擅自修改。

## 4. 本地交付

本地执行结束后写入 `feedback.md`。`MIRASIM_EVAL_VIEWER` 存在时交付 `<MIRASIM_EVAL_VIEWER>run/<slug>` 深链，不另起 viewer；不存在时交付 session 绝对路径，并说明可用 `mirasim eval` 打开。显式接平台时改按 `cli.md` 回写与回执合同。

深链不拼语言参数：viewer 按 `session.json.language` 选默认语言。页面分享出的 HTML 只有这条记录本身的语言；需要英文分享报告，就以英文运行并生成该 session。

## 5. 反馈检查

- 回答用户原问题，区分事实、专业判断、解释、未知与装置限制。
- TL;DR 为三到五条结论句，第一条就是本轮最重要判断。
- 所有重要判断与需求都有有效 case / step / evidence 回指。
- 需求与实现方案分开，优先级解释后果、证据与覆盖范围。
- 没把使用轨成功当成设计通过，也没把 reviewer 意见伪装成用户失败。
- 交付位置、结论边界和 `session.json.language` 已说明。
