# 获得修改授权后的 Feedback → 修改 → 复验合同

> 只有用户明确授权优化、修复、持续改进或达到某个结果时读取本页。单轮“看看 / 评测 / 给反馈”不要加载，也不得修改目标。

## 目录

1. 每轮留痕与处置账
2. 首轮广度与结构候选
3. 补丁、综合或另起
4. 修改与干净复验
5. 收敛闸
6. 另起版 A/B 留档
7. 收尾检查

## 1. 每轮留痕与处置账

修改前保存被验证版本、目标指纹和原始产物；修改后保存 diff、新指纹与独立轮目录。`feedback.md` 固定增加 `## 改进项处置账`。每份验真通过的 trace 中，每条可执行需求或 finding 在聚合前获得稳定 ID；重复项可以合并，但必须列全 source IDs，不能先从长 trace 筛成短报告后静默丢项。

| ID | 来源 | 证据 | 优先级 | 处置 | 状态 | 理由 | 改动引用 | 复验证据 |
|---|---|---|---|---|---|---|---|---|
| F-01 | source IDs | case/step/evidence | 高/中/低 | adopted / deferred / rejected | planned / implemented / verified / open / closed | 为什么 | diff / 文件 / 指纹 | 新 case 或 pending |

- `adopted`：决定采用，先为 `planned`；实现并给改动引用后为 `implemented`；拿到全新证据后才是 `verified`。
- `deferred`：保持 `open`，写阻塞条件、责任边界和重开条件；“交给 owner”不是充分理由。
- `rejected`：写与目标、证据、事实或取舍冲突在哪里，再置为 `closed`；新独立证据重提时自动打开。

目标范围内的高优项不能 deferred 后宣布收敛：要么 adopted 并验证，要么用可反驳的证据、事实或用户明确取舍 rejected。用户决定暂停时写“用户决定停止，`converged: false`”。

## 2. 首轮广度与结构候选

使用轨的用途广度放在第一轮：覆盖会改变理解、路径、约束或决定的不同用途，后轮才按受影响路径收窄。不要首轮只跑一小撮人，之后永远复用同一阵容。

被测物是主代理刚生成、且存在不同结构前提的创作目标时，首轮拿两三个前提不同的候选同批盲测。每个候选用中性名字并写一句内部前提；case 不知道原版、实验设置或作者偏好。先让证据选择和杂交结构，再进入打磨。

**图类候选直接生图（贯穿所有轮次的候选生成，含另起版）**：有生图能力就直接生成——宿主模型原生能出图，或装置已有 / 按 equip.md §B 引入的生图通道——候选由模型直接产出图片文件，打磨轮有图生图就带参考图改、没有就改提示重出。确认没有生图能力才退回代码渲染兜底：子代理写 HTML/SVG/mermaid，装置按固定 viewport 截成图片，那张图就是候选的交付形态，源码不进任何 case 的可见范围。有没有生图能力是装置事实，preflight 确认一次并留痕，本轮走了哪条路径写进留档（session.json 与 ab.md）；对跑两版必须同路径同口径（图对图），否则赢的可能是形态不是结构。主代理的事实核对不分路径：**用视觉逐字核对**图中文字、连线与素材事实清单一致（直接生图时文字与箭头错乱高发，代码渲染时溢出截断高发），核不过就重出，仍不过的候选不进盲测。

## 3. 补丁、综合或另起

每轮显式判断：补丁、综合还是另起。判补丁不是默认档，也要逐条说明结构信号为什么不成立。

结构信号包括：

- 不同用户的受阻落在同一结构层而非同一元素；
- 多个修改在争抢第一屏、开头、主操作位等同一稀缺位置；
- 连续两轮一维上涨、另一维钉住；
- 改动清单几乎全是“再加一块”；
- 用户每轮都返工同一处；
- 当前组织方式建立在用户不关心的前提上。

命中两条以上，至少准备一个换前提候选。判之前做换手检查：先自问“若这版不是我做的，只看 traces 和 feedback 会怎么判”并留档；拿不准就让不知道作者、只读证据的子代理给判定建议。推翻建议时把反证一并留档。

另起版由没见过现版本的全新子代理隔离生成：只给事实素材、需求清单和要采用的新前提，主代理只做事实核对。说不清换掉哪条前提就是换皮，不算另起。

Case 中出现的具体替代结构具有强制力，下一轮必须物化为候选之一，不能只放进需求清单。

## 4. 修改与干净复验

1. 先完成处置账，adopted 项从 `planned` 开始。
2. 按授权范围修改目标，保存 diff 与新指纹，更新为 `implemented`。
3. 为新版本建立新轮目录和 bundle。
4. 用全新子代理复验真正受影响的路径：每条已修高优用户需求至少一个受影响 case，再加入至少一个没看过修改过程、用途不同的新人物。
5. 用行为与外部证据描述变化，不只报分数；拿到新证据后才把 adopted 项改为 `verified`。

同一个 persona 换新进程只能证明干净复验，不增加用户覆盖面；要扩覆盖必须换人物经历或用途。未受影响路径不必机械全跑，但声称“整体更好”需要同口径可比较版本，声称“充分完成”还需要没看过修改过程的新视角。

## 5. 收敛闸

只有连续两轮同时满足以下条件才写 `converged: true`：

- 没有新增高优需求或 finding；
- 上轮所有 adopted 项都有对应的新证据；
- 处置账没有目标范围内未解决的高优项；
- 继续增加同类视角已不再改变决策，且至少有未参与修改过程的新人物支持广泛结论。

以下轮次不计入连续两轮：

- 只做元素微调，却没有检验任何结构前提或加入能发现新问题的视角；
- 固定人物已经任务饱和，只能继续重复相同成功路径；
- 评测装置、入口或证据链失效，结果只能靠代理自述。

反复返工却每轮被归为“个人习惯”的行为是高优信号。饱和的是这批视角，不是整个目标；要么换用途不同的人，要么如实写“在当前视角下饱和”，不能冒充全局收敛。

## 6. 另起版 A/B 留档

另起必须赢：补丁版与另起版使用同一批 case、同一口径、全新上下文和相同事实基础。另起版赢才换；输就保留现结构，平局也不自动换。事实基础有差异时，明确哪些优势不能归因于结构。

目录保留两版与判决：

```text
rounds/rN/
  patch/    traces/  measures.json
  rebuild/  traces/  measures.json
  ab.md
```

`ab.md` 写事实一致性、采用版、替换/保留的前提和证据依据。落选版本与 trace 不删除；判决不能只活在对话里。

## 7. 收尾检查

- 授权范围与实际修改一致；修改前后版本、指纹和 diff 齐全。
- 所有 actionable finding 已入账，无静默丢项。
- adopted/deferred/rejected 与状态生命周期、理由、改动和复验证据相符。
- 补丁/综合/另起判定与换手检查已留档。
- 替代结构已物化；另起版由没见现版的子代理生成并与补丁版同口径比较。
- `converged: true` 前没有未解决高优项，连续轮与新视角证据成立。
