# FlyWiki 图谱与 LLM Wiki 设计

> 版本：v0.1 · 日期：2026-07-19 · 状态：产品与技术联合设计草案

相关文档：[PRD](archive/PRD-FlyWiki.md) · [产品场景定义](archive/产品场景定义.md) · [首次历史输出回放](archive/历史输出回放-产品可行性报告.md)

## 一、设计目标

第二个场景的核心问题不是“没有图”，而是普通 RAG 在回答时直接拼接片段，缺少长期结构：

- 同一观点散落在多份资料中；
- 片段与片段之间的支持、反驳和限制关系没有被保存；
- 新旧信息没有时间和替代关系；
- 系统综合结论与用户自己的认知混在一起；
- 用户下一次搜索时，系统又从零开始拼接。

本设计的目标是：

> 把一次次临时 RAG 回答，转化为可持续更新、可追溯、可修订的主题 Wiki；同时用图结构保存“为什么得出这个结论”，而不是只保存结论文本。

## 二、明确不做

“图谱化”不等于：

- 把每个文档画成一个节点；
- 只根据向量相似度连接内容；
- 自动抽取大量人物和名词后形成蜘蛛网；
- 用图数据库替代全部检索；
- 让用户手工维护所有节点和边；
- 把模型生成的关系默认为事实；
- 每次提问都把整个图放进模型上下文。

图是底层结构和局部探索方式。默认用户界面仍然是可阅读的主题页、观点矩阵、时间线和证据工作台。

## 三、为什么普通 RAG 容易片段化

典型 RAG 流程是：

```text
问题
→ 将问题向量化
→ 找出相似文本片段
→ 把 Top K 片段放入提示词
→ 模型生成一次性回答
```

它在“找一段相关内容”时很好用，但有五个结构性限制：

1. **检索单位是片段**：片段不知道自己属于哪个完整论证；
2. **关系在查询时才临时推断**：支持、冲突和因果关系不会持久保存；
3. **没有稳定主题状态**：每次回答可能使用不同片段，结论容易漂移；
4. **缺少时间语义**：旧数据、预测和当前事实可能同时被召回；
5. **缺少用户认知层**：模型不知道哪些判断是用户明确认可过的。

FlyWiki 保留 RAG 作为召回工具，但检索对象从单一片段扩展为 Source、Evidence、Claim、Topic Wiki 和 Belief，并在回答前构造与当前问题相关的局部子图。

## 四、核心对象

### 4.1 Source：原始来源

不可变的原始资料或稳定快照，例如网页、PDF、截图、报告、视频转写和用户笔记。

关键字段：

- 来源类型、标题、作者、发布日期；
- 原始 URL 或本地文件位置；
- 内容哈希和导入时间；
- 允许访问范围和删除状态；
- 解析版本与处理状态。

### 4.2 Fragment：可定位片段

Source 中可以精确定位的最小上下文单元。它不是最终知识，只是引用定位工具。

关键字段：

- Source ID；
- 正文文本或 OCR 文本；
- 章节、页码、段落、视频时间戳或截图坐标；
- 前后上下文；
- 内容哈希。

### 4.3 Evidence：证据

从 Fragment 中识别出的、能对某个 Claim 产生作用的原文、数据、表格或图像。

Evidence 必须记录：

- 它支持、反驳或限制哪个主张；
- 它能支持主张的哪一部分；
- 它明确不能证明什么；
- 来源是一手规则、一手数据、产品自述、开源实现还是第三方评价；
- 是否经过用户核验或独立来源交叉验证；
- 适用的时间、地区、样本和对象。

### 4.4 Claim：主张

可以被支持、反驳、限制或替代的完整陈述。

好的 Claim：

> Android 10 及以上版本限制后台应用访问前台应用的剪贴板内容。

不好的 Claim：

> Android 隐私。

Claim 关键字段：

- 主张文本；
- 类型：事实、定义、观点、预测、建议；
- 适用条件和时间；
- 当前状态：候选、有依据、有争议、被替代、已撤回；
- 创建方式：来源抽取、系统推断、用户创建；
- 版本和规范化表达。

### 4.5 Entity：实体

人物、组织、产品、技术、地点、事件和概念。实体用于消歧、导航和限定范围，不直接等于知识结论。

### 4.6 Topic：主题

一组围绕用户长期问题组织的 Claim、Evidence 和 Entity。Topic 不是静态文件夹，可以同时包含多个子问题和争议。

### 4.7 Wiki Revision：主题 Wiki 版本

系统基于 Topic 当前有效的 Claim 和 Evidence 编译出的可阅读版本，包括：

- 当前结论；
- 核心概念和机制；
- 共识与争议；
- 时间线；
- 关键证据；
- 证据缺口；
- 与上一版本相比发生的变化。

Wiki 是派生结果，不是不可变事实。任何段落都必须能追踪到 Claim，再追踪到 Evidence 和 Source。

### 4.8 Belief：我的认知

用户明确表达或确认过的判断。它与 Claim 分开，因为“资料中存在某个观点”不代表用户认可该观点。

Belief 记录：

- 用户确认的判断；
- 置信程度；
- 适用边界；
- 形成时间和确认方式；
- 依据了哪些 Claim/Evidence；
- 被哪个新版本强化、细化、挑战或替代。

### 4.9 Output Task：输出任务

一次真实写作、报告、研究或决策任务。它提供检索上下文，避免系统只按主题相似度排序。

关键字段：

- 用户要回答的问题；
- 准备表达的主张；
- 输出类型和受众；
- 时间范围和证据标准；
- 选用、拒绝和核验过的证据；
- 最终结论和认知回写结果。

## 五、关系类型

### 5.1 证据与主张

| 关系 | 含义 | 示例 |
|---|---|---|
| `SUPPORTS` | 证据直接提高主张成立的可能性 | 官方规则支持平台限制主张 |
| `REFUTES` | 证据直接反驳主张 | 竞品已有功能反驳“市场无人覆盖” |
| `LIMITS` | 证据限制主张适用范围 | 只在特定系统版本或用户群成立 |
| `QUALIFIES` | 增加条件，使表达更准确 | 从“不能访问”改为“后台不能访问前台剪贴板” |
| `SUPERSEDES` | 新证据或主张替代旧版本 | 新法规替代旧规则 |
| `MENTIONS` | 只提及主题，不构成论证 | 一篇文章提到 RAG，但没有评价效果 |

### 5.2 主张与主张

| 关系 | 含义 |
|---|---|
| `DUPLICATES` | 语义相同或等价表达 |
| `CONTRADICTS` | 在相同条件下不能同时成立 |
| `REFINES` | 新主张增加条件或精度 |
| `GENERALIZES` | 更宽范围的上位主张 |
| `CAUSES` | 声称存在因果关系，必须有依据 |
| `DEPENDS_ON` | 一个主张依赖另一个前提 |
| `PRECEDES` | 时间上发生在另一个事件或状态之前 |

### 5.3 认知关系

| 关系 | 含义 |
|---|---|
| `BELIEVES` | 用户确认某个 Claim 或修订表达 |
| `REINFORCES_BELIEF` | 新证据强化已有认知 |
| `CHALLENGES_BELIEF` | 新证据与已有认知不一致 |
| `NARROWS_BELIEF` | 缩小适用范围 |
| `LOWERS_CONFIDENCE` | 不撤回观点，但降低置信度 |
| `RETRACTS_BELIEF` | 用户因证据不足或反例撤回认知 |
| `REPLACES_BELIEF` | 新认知版本替代旧版本 |

### 5.4 关系的来源等级

每条边必须标记产生方式：

- `extracted`：来源原文明确表达；
- `inferred`：模型根据多条内容推断；
- `user_confirmed`：用户明确确认；
- `user_rejected`：用户明确否定；
- `rule_derived`：由确定性规则生成，例如同内容哈希去重。

界面默认不能把 `inferred` 关系显示成与 `user_confirmed` 或原文明确表达同等确定。

## 六、三个相互连接但不能混同的图

### 6.1 来源追踪图

```text
Source → Fragment → Evidence → Claim → Wiki 段落
```

回答“这句话从哪里来”“删除来源会影响什么”。

### 6.2 知识关系图

```text
Claim ↔ Claim
Claim ↔ Entity
Claim ↔ Topic
Evidence → Claim
```

回答“哪些观点一致、冲突、依赖或已经被替代”。

### 6.3 个人认知图

```text
User → Belief Revision → Claim/Evidence
Output Task → Adopted Evidence → Belief Revision
```

回答“我过去怎么想、为什么改变、当前还相信什么”。

这三个图可以存储在同一数据库中，但产品必须提供不同视图和权限。系统不能因为知识图中有某个 Claim，就自动在个人认知图中创建 `BELIEVES`。

## 七、必须满足的系统不变量

1. **原始来源不可被生成内容覆盖**；
2. **任何 Wiki 陈述必须能追踪到至少一个 Claim**；
3. **任何有依据 Claim 必须能追踪到至少一个 Evidence 和 Source**；
4. **模型推断的关系必须明确标为 inferred**；
5. **冲突不能通过摘要自动消失**；
6. **Belief 必须经过用户明确确认或来自用户原文中的明确表达**；
7. **未确认的认知候选不能以“你认为”呈现**；
8. **删除 Source 后必须重新计算受影响 Claim、Wiki 和 Belief 依据**；
9. **被替代内容保留历史，但不默认参与当前结论**；
10. **绝对表达必须检查反例、范围和时间**；
11. **相关性高不能自动等同于直接证据**；
12. **证据必须记录能证明什么和不能证明什么**。

## 八、摄取与更新管线

### 8.1 第一次摄取

```text
1. 保存 Source 原文/快照
2. 解析为可定位 Fragment
3. 提取作者、时间、章节、表格和实体
4. 抽取候选 Claim 与 Evidence
5. 给 Evidence 标记来源类型、范围和原文定位
6. 与已有 Entity 和 Claim 做消歧、去重
7. 建立候选关系
8. 计算受影响 Topic
9. 生成 Wiki 修订提案
10. 如涉及用户认知，生成 Belief 更新建议
```

### 8.2 新资料进入已有主题

系统不是重新总结整个主题，而是先计算变化：

```text
新 Claim
→ 与当前 Claim 比较
→ 重复 / 支持 / 细化 / 冲突 / 替代 / 无法判断
→ 识别受影响 Wiki 段落和 Belief
→ 生成结构化 Diff
→ 更新系统 Wiki
→ 给用户发送少量认知变化卡
```

### 8.3 Wiki 编译提案

每次编译输出的不只是新页面，还必须包括：

- 新增了哪些陈述；
- 修改了哪些陈述；
- 删除或降级了哪些陈述；
- 哪些证据触发了变化；
- 是否产生新冲突；
- 哪些页面和认知可能已经过期；
- 是否有来源不足或模型无法判断的部分。

### 8.4 用户认知更新

系统为 Belief 生成建议时，用户可以：

- 接受；
- 修改后接受；
- 降低或提高置信度；
- 缩小适用范围；
- 拆成多个主张；
- 暂停判断；
- 只保留为资料；
- 撤回旧认知；
- 标记来源不可信或与自己无关。

## 九、四种问题驱动检索

### 9.1 恢复主题全貌

用户问题：

> “我以前收藏过哪些关于 AI Agent 长期记忆的内容？现在应该怎样理解这个主题？”

系统输出：当前结论、概念结构、主要方案、时间线、争议、我的认知和知识缺口。

### 9.2 检验一个主张

用户问题：

> “个人知识库的核心壁垒不是向量检索，而是认知状态和证据关系。”

系统输出：主张拆分、直接支持、直接反例、限制条件、背景材料、不能证明的部分和建议修订。

### 9.3 对照我的认知

用户问题：

> “最近的新资料改变了我对 AI 知识库的哪些看法？”

系统输出：已有 Belief、相关新证据、新增/强化/挑战/替代关系和待确认更新。

### 9.4 追踪来源影响

用户问题：

> “如果删除这份过期报告，哪些主题结论和我的判断会失去依据？”

系统沿来源追踪图返回受影响的 Evidence、Claim、Wiki 段落和 Belief。

## 十、检索与综合流程

### 10.1 查询理解

先识别：

- 用户是在找资料、恢复主题、检验主张还是对照认知；
- 输出类型和受众；
- 时间、地区、样本和来源要求；
- 用户表达中是否存在多个复合主张；
- 是否包含“全部、唯一、无人、必然”等需要反例检查的表达。

### 10.2 多路召回

同时执行：

- 全文检索：找准确术语、数字、标题和引用；
- 向量检索：找语义相近但措辞不同的内容；
- 实体检索：找同一人物、公司、产品和别名；
- Topic/Wiki 检索：找已有结构化主题；
- Claim 检索：找已有观点和冲突；
- Belief 检索：找用户过去确认过的判断；
- 时间检索：优先适用时间匹配的内容。

### 10.3 候选归一化

- 合并相同 Source 的重复片段；
- 合并等价 Claim；
- 处理实体别名；
- 分离同一来源的转载和独立来源；
- 排除已删除或已失效内容；
- 保留与主张相反但高质量的候选。

### 10.4 构造局部子图

从当前问题涉及的 Claim、Topic 和 Belief 出发，只扩展有限关系：

- 直接 Evidence；
- 一跳冲突、细化和替代 Claim；
- 必要的前提 Claim；
- 相关实体和时间节点；
- 用户已确认 Belief。

默认不把全局图全部装入上下文。

### 10.5 证据评估

每条候选分别评估：

| 维度 | 问题 |
|---|---|
| 查询相关性 | 是否直接回答当前问题 |
| 主张直接性 | 是否直接支持/反驳，还是只提及主题 |
| 来源类型 | 官方规则、一手数据、产品自述、第三方评论或未知 |
| 独立性 | 多个来源是否真正独立 |
| 时效 | 是否仍然适用 |
| 范围匹配 | 样本、地区、用户和条件是否一致 |
| 原文可核验 | 是否能定位到完整上下文 |
| 用户状态 | 未读、机器处理、用户已读、用户已确认 |

系统可以用这些维度排序，但不向用户隐藏为单一“可信分”。

### 10.6 综合输出

输出顺序：

1. 拆分后的主张；
2. 我的既有认知；
3. 系统当前结论；
4. 一致、新增、冲突和过期部分；
5. 支持、反对、限制、背景和证据缺口；
6. 建议的更准确表达；
7. 每条结论的原文定位；
8. 用户确认后的认知更新。

## 十一、排序策略

### 11.1 两阶段排序

第一阶段追求召回：

- 全文 BM25；
- 向量相似度；
- 实体和主题匹配；
- 图关系邻近；
- 时间范围匹配。

第二阶段追求证据可用性：

- 与当前主张的直接关系；
- 来源和独立性；
- 范围与时间；
- 原文定位完整度；
- 用户确认状态；
- 与已有证据的重复程度；
- 是否提供重要反例。

### 11.2 不能只优化点击率

如果只根据用户过去点击或接受过的内容排序，系统可能持续强化用户原有观点。排序必须为高质量反例保留固定位置，并明确说明它与用户认知的冲突。

## 十二、建议的逻辑数据表

首版不要求专用图数据库。关系数据库即可支持图查询和版本控制：

| 表 | 用途 |
|---|---|
| `sources` | 原始来源与权限 |
| `source_versions` | 来源快照和内容哈希 |
| `fragments` | 可定位原文片段 |
| `evidence` | 证据内容、范围和核验状态 |
| `claims` | 规范化主张和状态 |
| `claim_evidence_edges` | 支持、反驳、限制等关系 |
| `claim_claim_edges` | 冲突、细化、替代、依赖等关系 |
| `entities` | 规范化实体 |
| `entity_aliases` | 实体别名和消歧 |
| `claim_entity_edges` | 主张涉及的实体和角色 |
| `topics` | 主题和子问题 |
| `topic_claim_edges` | 主题包含或依赖的主张 |
| `wiki_revisions` | 每次 Wiki 编译的版本 |
| `wiki_revision_claims` | Wiki 段落到 Claim 的来源关系 |
| `beliefs` | 用户认知主体 |
| `belief_revisions` | 用户认知版本和确认记录 |
| `belief_claim_edges` | 认知与主张/证据关系 |
| `output_tasks` | 真实输出任务 |
| `task_claims` | 输出任务中的准备表达主张 |
| `task_evidence_selections` | 采用、拒绝和核验过的证据 |

## 十三、失败处理

### 13.1 实体无法消歧

保持为候选，不自动合并；提示用户或等待更多上下文。

### 13.2 主张是否冲突无法判断

标记 `ambiguous`，并展示双方适用条件，不让模型强行调和。

### 13.3 来源失效

保留合法保存的快照和哈希；若没有快照，则标记引用不可核验并降低使用优先级。

### 13.4 Wiki 编译出现无依据陈述

编译失败，不发布新版本；保留上一版本和失败诊断。

### 13.5 用户否定系统推断

保留拒绝记录，避免重复提出相同建议；不删除原始 Claim。

### 13.6 删除来源

先显示影响范围，再执行删除；删除后重新计算所有下游依据和 Wiki 状态。

## 十四、MVP 实现范围

### P0

- Source、Fragment、Evidence、Claim、Topic、Wiki Revision、Belief、Output Task；
- 支持、反驳、限制、补充、替代和提及关系；

## 十五、评估方法

### 15.1 基准数据集

需要建立：

1. 100 个混合格式来源的引用定位集；
2. 200 组人工标注的 Claim—Evidence 关系；
3. 50 组等价、冲突、细化和替代 Claim；
4. 20 个主题的十轮增量 Wiki 更新集；
5. 20 个真实输出任务及最终采用证据；
6. 10 组用户历史认知与新证据变化记录。

### 15.2 核心指标

| 能力 | 指标 |
|---|---|
| 原文定位 | 引用可打开率、页码/段落准确率 |
| 关系识别 | SUPPORTS/REFUTES/LIMITS/MENTIONS Precision/Recall |
| 主张去重 | 等价 Claim 合并准确率、错误合并率 |
| 冲突保留 | 关键反例召回率、冲突被错误消除率 |
| Wiki 编译 | 无依据陈述率、信息遗漏率、十轮后失真率 |
| 认知隔离 | 未确认推断误标为用户认知的次数 |
| 输出价值 | Time to Evidence、Precision@5、最终采用率 |
| 长期价值 | 第二次输出任务使用率、证据复用率、认知修订率 |

## 十六、产品判断

真正的产品壁垒不是“有一个图数据库”，而是：

1. 能否从杂乱资料中稳定抽取可判断主张；
2. 能否把支持、反驳、限制和时间关系保存下来；
3. 能否持续编译 Wiki 而不丢失来源和少数观点；
4. 能否把系统知识与用户认知严格分开；
5. 能否在真实输出时生成比片段式 RAG 更可用的认知对照和证据包。

只有第五点在用户任务中成立，前四点的工程复杂度才值得投入。
