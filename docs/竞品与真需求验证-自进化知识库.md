# 竞品与真需求验证：自进化知识库 / 垂直认知顾问

- 日期：2026-07-22
- 研究范围：个人知识管理、证据研究、企业知识搜索、开源 RAG/自动 Wiki
- 结论用途：修订 `PRD-FlyWiki-垂直认知顾问.md` 的产品需求与实验门槛

## 1. 结论先行

### 1.1 真需求存在，但要分成两层

**已经被市场验证的基础需求：**

1. 用户愿意为“收藏、阅读、重新发现”付费；
2. 专业用户愿意为“系统化搜索、证据抽取、可审计引用”付费；
3. 企业愿意为“跨系统、权限感知的知识搜索与问答”支付高额费用；
4. 用户不想维护复杂文件夹，希望系统自动组织、召回和生成可用成果。

**尚未被验证的 FlyWiki 差异化需求：**

1. 用户是否愿意显式定义长期 Mission 和持续问题；
2. 相比摘要、研究报告和普通 RAG，用户是否更需要“认知变化卡”；
3. 用户是否会确认、修订并复用一份长期结论；
4. “支持—反驳—限制—背景”的证据包是否能显著改善真实输出；
5. 该价值是否足以让个人持续付费，而不是偶尔使用 NotebookLM、Notion 或通用 Deep Research。

因此，正确的产品判断是：

> “知识过载与证据研究”是真需求；“持续维护用户结论”是有差异化潜力但尚未验证的产品假设。

不能因为竞品很多就直接开始开发完整产品，必须先用真实任务证明差异化层成立。

### 1.2 推荐定位

FlyWiki 应定位为：

> 面向持续输出的专业个人和小型研究团队，在现有知识库之上维护“当前结论、认知变化与可引用证据”的任务层。

它不是：

- 新的通用第二大脑；
- 新的 NotebookLM；
- 新的企业搜索/RAG 平台；
- 自动生成数百个 Wiki 页面的知识图谱产品；
- 心理诊断或证券投资建议工具。

## 2. 市场与用户任务

### 2.1 市场不是一个品类，而是四段工作流

| 工作段 | 用户任务 | 已有代表产品 | 市场成熟度 |
|---|---|---|---|
| Capture | 收下网页、文档、邮件、视频与笔记 | Readwise Reader、Mem | 成熟且有个人订阅 |
| Understand | 基于指定资料理解、问答、生成摘要 | NotebookLM、ima、通用文件问答 | 已成为大模型标配 |
| Retrieve | 从个人或企业知识中找到可信答案 | Glean、Notion AI、飞书知识问答、WeKnora | 企业市场成熟、竞争激烈 |
| Synthesize & Revise | 围绕一个长期问题综合正反证据、修订结论、服务输出 | Elicit 部分覆盖；其他产品多为一次性报告 | 仍有产品空位，但需求强度待验证 |

FlyWiki 只能在第四段建立产品价值。前三段应复用或集成，不应重做。

### 2.2 最值得服务的用户

首批目标用户应有可观察的“输出责任”，而不是泛兴趣：

- 产品经理或创业者：需要持续判断产品与行业方向；
- 技术/产业内容作者：需要每周或每月输出带出处的内容；
- 咨询顾问、研究员：需要把分散资料组织为结论和证据；
- 小型研究团队：需要知道团队当前共识、争议与结论依据。

排除：只收藏不输出、偶尔问一个文件、只想听摘要、没有固定主题的用户。

## 3. 五个主要竞品

### 3.1 Google NotebookLM

**定位与商业模式**

- 面向个人、教育和工作用户的 source-grounded research assistant；
- 免费版可创建 100 个 notebook、每个 50 个来源；Workspace 和 Google AI 计划提供更高额度与企业级数据保护；
- 支持 PDF、网页、YouTube、音频、Google Docs/Slides/Sheets 等来源。

官方说明明确强调回答基于用户来源并带行内引用，点击引用可跳到原文位置；还能生成 briefing、study guide、mind map、audio/video overview、slide deck 等成果。[NotebookLM 产品说明](https://support.google.com/notebooklm/answer/16164461?hl=en) [NotebookLM 引用机制](https://support.google.com/notebooklm/answer/16179559?hl=en) [Workspace 额度与数据保护](https://support.google.com/notebooklm/answer/16337734?hl=en)

**优势**

- 来源选择清晰，回答与原文引用体验成熟；
- 多种“理解产物”降低资料进入门槛；
- Google 生态分发、模型和数据安全能力强；
- Fast Research / Deep Research 可以直接发现并导入新来源。

**缺口**

- notebook 仍以一次研究项目或一组资料为中心；
- 主要交付摘要、问答和内容成品，不维护用户确认过的长期结论；
- 不主动说明“新来源相对上周改变了什么”；
- 没有把证据显式分成支持、反驳、限制和背景。

**FlyWiki 应借鉴**

- 来源勾选与回答作用域必须始终可见；
- 引用 hover 预览、点击回原文应成为硬标准；
- 先生成“可消费成果”，不要要求用户浏览知识图谱；
- 允许把一次 Deep Research 的报告及来源加入长期 Mission，但不自动当成确认结论。

### 3.2 Elicit

**定位与商业模式**

- 面向科研、生命科学、尽调和专业研究的证据综合工具；
- 免费版提供论文搜索和查看来源；Plus 为 11 美元/月（年付），Pro 为 39 美元/月（年付），Pro 支持最多筛选 5,000 篇论文的系统综述工作流。[Elicit 定价](https://elicit.com/pricing)
- Research Agent 会先拆解研究任务、询问范围、搜索多类来源，再输出结构化表格或报告；强调所有断言基于证据。[Elicit Research Agent](https://elicit.com/blog/introducing-research-agent-workflows)

**需求信号**

Elicit 公开的 API/MCP 案例包括持续运行的研究管线、尽调、药企研究和写作时自动找证据；案例声称有任务能减少约 20 小时前期研究，另有团队预计减少 80% 准备时间。这里属于供应商案例，应作为假设来源而不是独立审计结果。[Elicit API 与客户工作流](https://elicit.com/blog/the-elicit-api-and-mcp-powering-autonomous-research-engines)

**优势**

- 研究问题先澄清、再执行，而不是直接给答案；
- 筛选、抽取、表格、报告各阶段相对可审计；
- 结构化 evidence table 非常接近专业用户实际工作；
- 支持迭代研究和 API/MCP 嵌入。

**缺口**

- 强项仍是一次研究流程和学术证据；
- 没有维护个人对主题的长期结论版本；
- 不负责日常收藏的低成本分流；
- 通用产品、产业和内部资料研究仍在扩展期。

**FlyWiki 应借鉴**

- 正式研究前展示研究计划、范围、来源类型和输出格式；
- 证据包首先是结构化表格，其次才是自然语言报告；
- 每个筛选/舍弃决定保留原因，便于审计；
- 把“信息不足”作为合法结果，而不是强行生成结论。

### 3.3 Readwise Reader

**定位与商业模式**

- 面向 power readers 的统一阅读、稍后读、标注和回顾产品；
- Readwise + Reader 年付 9.99 美元/月，月付 12.99 美元/月，无永久免费版。[Readwise 定价](https://readwise.io/pricing/reader)
- 官方首页直接把痛点定义为：保存速度超过处理速度，稍后读列表会随着时间变得更糟；产品用 inbox triage、阅读、标注和 Daily Review 处理内容过载。[Readwise Reader](https://readwise.io/read)

**优势**

- 真实抓住“存了但没时间看”的入口痛点；
- inbox triage 强调清空与处理，而不是持续堆积；
- highlight、tag、note、export 和 Daily Review 形成习惯回路；
- 能导出到 Obsidian、Notion 等现有工具，不强迫用户迁移所有工作流。

**缺口**

- 用户仍需阅读和判断；
- Daily Review 主要帮助记忆，不维护主题结论；
- 标注是片段资产，没有自然形成支持/反驳的证据结构；
- 输出环节仍依赖其他写作工具。

**FlyWiki 应借鉴**

- 首页应是有容量限制的认知 inbox，而不是知识库目录；
- 每条新信息必须能“接受、稍后、忽略、永不再推”；
- 用每天最多 3 条、每周最多 10 条的内容预算建立信任；
- 输出到用户已有写作环境，避免把 FlyWiki 做成全功能编辑器。

### 3.4 Mem

**定位与商业模式**

- 面向个人与小团队的 AI notes / self-organizing workspace；
- 免费版有笔记、聊天与 PDF 页数限制；Pro 为 12 美元/月（年付），Teams 为定制价格。[Mem 定价](https://get.mem.ai/pricing)
- 产品强调低整理成本、自然语言召回、相关笔记和 shared collections。[Mem 团队使用说明](https://help.mem.ai/guides/using-mem-as-a-team)

**优势**

- 捕获摩擦低，用户不需要先设计文件夹；
- related notes 在写作过程中主动浮现；
- 个人到小团队的路径自然；
- 通过会议、邮件和笔记捕获形成持续上下文。

**缺口**

- 自动关联不等于形成可靠结论；
- 对证据质量、反证和原文引用的要求较弱；
- 仍以 note/chat 为交付单位；
- 团队能力更像共享笔记，不是共同结论治理。

**FlyWiki 应借鉴**

- Mission 初始设置必须轻，允许系统从用户最近任务建议持续问题；
- 在用户写观点时主动浮现相关证据，而不是要求离开当前页面搜索；
- Capture 与“认知晋升”分离：所有内容可进入，但只有少量内容影响结论。

### 3.5 Glean

**定位与商业模式**

- 面向大中型企业的权限感知搜索、Assistant、Agent 和 enterprise context 平台；
- 连接企业应用，构建 enterprise graph 与 personal graph，支持权限、身份、治理和执行；
- 采用企业销售和定制报价。

Glean 于 2026 年 5 月披露 ARR 超过 3 亿美元，并称 Fortune 500 客户数量同比接近翻倍。该数字来自公司公告，但足以证明企业在为可信企业上下文和搜索大规模付费。[Glean ARR 公告](https://www.glean.com/press/glean-surpasses-300m-arr-unrivaled-enterprise-context-fuels-ai-adoption) 其平台将 connectors、search、enterprise graph 和 enterprise memory 作为基础能力。[Glean 平台](https://www.glean.com/platform)

**优势**

- 企业数据连接、权限继承、治理、审计能力成熟；
- 产品直接进入员工工作流，而不是只提供独立知识库；
- 从 search 扩展到 assistant、agent、meeting context 和 skills；
- 企业采购价值与规模已经被商业结果验证。

**缺口**

- 重点是“找到组织上下文并执行工作”，不是维护某个研究主题的共同结论；
- 企业部署与集成成本高，不适合早期个人产品复制；
- 强平台路线会让 FlyWiki 的探索型能力失去焦点。

**FlyWiki 应借鉴**

- 企业版必须继承原系统权限，不能另建一套不安全索引；
- 结论必须有 owner、版本、确认人和审计记录；
- 应嵌入 Slack/飞书/文档等工作流，而不是要求所有员工打开新应用；
- To B 必须围绕可量化业务任务售卖，而不能卖抽象的“知识更智能”。

## 5. 开源替代方案

| 项目 | 公开信号 | 竞争意义 |
|---|---|---|
| Onyx | GitHub 约 29.8k stars；50+ connectors、Agentic RAG、Deep Research、Agents、RBAC、SSO、审计，MIT 核心版。[GitHub](https://github.com/onyx-dot-app/onyx) | 企业 RAG/Chat/Agent 已有成熟开源替代，FlyWiki 不应投入底层平台竞争 |
| Khoj | GitHub 约 34.7k stars；个人 AI、文档/网络问答、定时研究、newsletter、Obsidian、多端、自托管。[GitHub](https://github.com/khoj-ai/khoj) | “个人知识 + 自动研究 + 通知”已有强替代，认知变化必须比 newsletter 更有价值 |
| SurfSense | GitHub 约 14.4k stars；NotebookLM 开源替代、连接器、引用报告、scheduled workflows、Obsidian 同步。[GitHub](https://github.com/MODSetter/SurfSense) | 报告、自动化和本地隐私不是独占能力 |
| OpenKB | GitHub 约 1.9k stars；把原始资料编译为结构化 Wiki，支持长文档与问答。[GitHub](https://github.com/VectifyAI/OpenKB) | “LLM 自动生成 Wiki”正在快速同质化，也验证了页面膨胀风险 |
| LLM Wiki | 本地自动 Wiki、Review、Graph、Deep Research | 最接近 FlyWiki 的知识编译层，但仍未解决任务驱动的结论与证据闭环 |

开源市场提供了第二个明确结论：连接器、RAG、问答、自动 Wiki、Deep Research、scheduled report 和本地部署都很难形成长期壁垒。

## 7. 从竞品反推的需求修订

### 7.1 必须加入 P0

1. **Source Scope**：用户能明确选择本次回答使用的资料范围，并看到哪些来源实际被采用。
2. **Research Plan Preview**：复杂任务先展示问题拆解、来源范围、时间范围、输出格式，用户可一键修正后执行。
3. **Evidence Matrix**：证据包默认用表格呈现 Claim、立场、原文、来源级别、日期、限制和采用状态。
4. **Scheduled Change Brief**：Mission 支持固定周期检查新资料，但只有超过价值阈值才通知。
5. **Info-not-found / Conflict**：证据不足、来源冲突、材料过期必须是一级结果类型。
6. **Evidence Feedback**：采用、弃用、引用错误、来源低质必须记录并用于后续排序。
7. **Export / In-flow Use**：P0 先做好 Markdown/复制，P1 再做浏览器、飞书、Notion 或 Obsidian 内嵌。

### 7.2 不应因竞品而加入 P0

- Audio/Video Overview、播客、幻灯片；
- 通用 Agent Builder；
- 全套企业 connectors；
- 知识图谱主界面；
- 全功能笔记编辑器；
- 公开知识库广场和知识付费；
- 邮件、会议、任务自动执行；
- 自建向量库、解析器和模型网关。

这些能力都已有成熟产品，且不能验证 FlyWiki 的核心假设。

## 8. 真需求实验方案

### 8.1 实验原则

- 只测试真实发生的工作，不问“你会不会用”；
- 先拿到用户最近完成的输出及其资料、时间记录，再讨论方案；
- 同一任务比较现有方法、普通 RAG 和 FlyWiki 交付；
- 付费或预算承诺比满意度更重要；
- 每个实验都设置停止条件，不能只收集正反馈。

### 8.2 E0：问题证据访谈

**对象**：8–12 名 AI/科技领域产品经理、作者、顾问或研究者。

**要求**：每人带来最近 30 天内完成的一个真实输出，以及当时使用的资料、搜索记录或引用。

记录：

- 从开始研究到提交输出的总时长；
- 资料数量、重复搜索次数、找回旧资料的时间；
- 最终用了多少证据、多少证据找不到原文；
- 输出后是否保留结论和证据；
- 同一主题下次是否重新开始。

**通过门槛**：

- ≥ 8 人中至少 6 人每月有两次以上同类输出；
- 其中至少 5 人单次“整理 + 找证据”超过 45 分钟；
- 至少 4 人能展示“以前看过但本次重新找”的具体证据；
- 至少 3 人已为 Readwise、Notion、AI 或研究工具付费。

**停止条件**：痛点只存在于创始人本人；多数用户只需要一次摘要；没有固定主题或持续输出。

### 8.3 E1：Concierge 认知变化周报

**对象**：从 E0 中选 5 人，每人选择一个持续问题，运行 2 周。

不开发完整产品，由人工 + WeKnora/LLM 完成：

- 每周接收 10–30 条资料；
- 只交付 3 张变化卡；
- 每张卡给出新旧差异、支持/反驳证据和原文；
- 记录用户是否打开、接受、修订、忽略，以及是否影响真实输出/决策。

**通过门槛**：

- 变化卡“值得看”比例 ≥ 70%；
- 每人两周至少接受或修改 1 次结论；
- 至少 3/5 用户主动提交第二周资料；
- 人工交付时间能控制在每用户每周 30 分钟以内，或看得到自动化后可成立的毛利。

**停止条件**：用户只想要新闻摘要；变化卡与普通周报没有显著差异；用户从不确认结论；人工审核成本不可压缩。

### 8.4 E2：证据包对照实验

对同一个真实输出任务生成两版：

- A：普通 RAG / NotebookLM 风格答案；
- B：FlyWiki Evidence Matrix + 当前结论 + 最强反证 + 限制条件。

随机隐藏产品名，让用户完成最终输出。

**通过门槛**：

- B 的证据准备时间比 A 降低 ≥ 40%；
- B 中 ≥ 60% 证据被采用；
- 引用定位正确率 ≥ 98%；
- 盲评中 B 在“可核验、完整、可直接使用”至少两项显著更好；
- 用户不是仅因 B 更长而偏好它。

**停止条件**：NotebookLM / Elicit / 普通 RAG 能以相同时长达到同等结果；正反分类没有提高输出质量；用户仍需重新打开搜索引擎找大多数证据。

### 8.5 E3：真实付费实验

不要只问愿付价格。提供 4 周陪跑服务：

- 个人版创始价格：99–199 元/月；
- 包含 1 个 Mission、每周变化简报、2 次证据包；
- 只允许真实支付或明确的公司报销/采购承诺进入“付费验证”。

**通过门槛**：5 名试用者中至少 3 人付费，4 周后至少 2 人主动续费；至少 1 人因为一次输出成果而推荐同类用户。

**停止条件**：用户只在免费时使用；愿意为“代做研究”付费但不愿为产品付费；服务成本远高于价格且无法自动化。

### 8.6 E4：企业部门验证

个人闭环通过后再做。选择一个 5–15 人的产品、研究或客户成功团队，以及一个可量化任务，例如竞品周报、售前证据或制度答疑。

前置条件：

- 有业务 owner 和预算 owner；
- 已有 WeKnora/飞书/Notion 等知识底座；
- 能提供权限边界和真实任务基线；
- 不要求 FlyWiki 在试点期承担全企业 SLA。

**通过门槛**：目标任务耗时下降 ≥ 30%，周活跃使用者 ≥ 60%，引用错误率 < 2%，试点结束有明确续费/预算流程。

## 9. 产品判定框架

| 实验结果 | 说明 | 下一步 |
|---|---|---|
| E0 不通过 | 目标人群或频次选错 | 更换垂直场景，不开发产品 |
| E0 通过、E1 不通过 | 有资料痛点，但认知变化不是解法 | 做轻量 Evidence Desk 或集成现有工具 |
| E1 通过、E2 不通过 | 周报有价值，但输出证据没有差异 | 聚焦 monitoring/brief，不做完整认知模型 |
| E2 通过、E3 不通过 | 有使用价值但付费弱 | 尝试团队/咨询交付，或降低成本后重测 |
| E3 通过 | 个人垂直产品初步成立 | 开发最小自动化产品 |
| E4 通过 | 企业部门场景成立 | 增加权限、审计与工作流集成 |

## 10. 最终建议

1. 暂停扩展通用知识库功能，先跑 E0–E2；
2. 首个垂直仍选择 AI/科技产业研究，但招募对象必须有真实输出责任；
3. Demo 只做 Mission、变化卡、确认结论、Evidence Matrix 和引用回原文；
4. 用 NotebookLM 或普通 RAG 作为对照组，证明差异化，而不是只和用户原来的手工流程比较；
5. 个人侧以 99–199 元/月测试真实支付；企业侧等个人闭环成立后再做部门任务试点；
6. 如果用户真正愿意付费的是“人工研究服务”，就先做 productized service，不要过早把它包装成 SaaS；
7. FlyWiki 的护城河若成立，应来自长期积累的“任务—结论版本—证据采用—认知变化”数据，而不是 RAG、图谱或自动 Wiki 技术。
