# 开源知识库“知识健康中心”能力调研

> 访问日期：2026-08-01
> 调研对象：[`nashsu/llm_wiki`](https://github.com/nashsu/llm_wiki)、[`Tencent/WeKnora`](https://github.com/Tencent/WeKnora)、[`eugeniughelbur/obsidian-second-brain`](https://github.com/eugeniughelbur/obsidian-second-brain)；末尾补充 [`VectifyAI/OpenKB`](https://github.com/VectifyAI/OpenKB) 原生基线。
> 证据范围：仅使用各项目官方 GitHub 仓库的 README、文档、源码与测试；结论对应调研时 `main` 快照，不把 README 宣传语单独当成已完整实现的证据。

## 结论摘要

这些项目都已经出现“知识健康”能力，但没有一个完整实现了 FlyWiki 所定义的、以 Claim—Evidence 为中心的知识健康中心。

- **WeKnora** 已有最接近服务端“健康中心”的真实后端能力：Wiki Lint、健康分、孤立页/断链/过期来源引用检查、自动修复、待处理 Issue、摄取任务与发布状态。但它的证据关系仍主要是“Wiki 页面 → 文档/Chunk”，不是“事实主张 → 精确证据跨度”，也没有完整的引用覆盖率、外部来源失效验证和不可变发布健康门禁。
- **llm_wiki** 的桌面产品交互最值得参考：独立 Lint、Graph Insights、Review、持久化摄取队列、重复页确认合并和可操作修复已经组成较完整的个人知识库维护体验。但来源追溯主要停留在页面 frontmatter 的 `sources[]`，语义矛盾和过期判断由 LLM 基于页面摘要完成，不是结构化 Claim 审计。
- **obsidian-second-brain** 不是一个完整知识库服务，而是“可执行脚本 + Obsidian 插件 + Agent 命令工作流”的混合工具包。重复、孤立、断链、索引覆盖和 freshness lint 是真实代码；语义矛盾扫描、来源权威性比较及多数修复编排仍主要是 Agent 工作流模板。它最值得借鉴的是 freshness policy、安全修复分级和显式确认原则。
- **OpenKB 自身已有 lint 基线**，包括结构断链、孤立页、raw 缺 Wiki 条目、索引同步、frontmatter/OKF 检查，以及 LLM 语义层的矛盾、缺口、过期、冗余和概念/实体覆盖报告。FlyWiki 不应重复实现这些基础扫描，而应在 OpenKB 扩展层增加 Claim—Evidence 健康、来源版本与发布门禁，再统一呈现在知识健康中心。

## 评估口径

| 标签 | 含义 |
| --- | --- |
| **完整具备** | 仓库内存在可运行实现、持久状态或产品入口，且覆盖该维度的主要语义；仅在该维度内成立，不代表完整的 FlyWiki 健康中心。 |
| **部分具备** | 有真实实现，但粒度较粗、范围有限、依赖 LLM 启发式判断，或缺少关键闭环。 |
| **没有发现** | 在本次检查的官方 README、文档和源码中没有找到支持该能力的证据；不等于证明任何分支或未来版本都不存在。 |
| **仅工作流模板** | 文档/Skill 指示 Agent 应如何扫描或修改，但没有相应的确定性服务、数据模型或检查器来保证执行结果。 |

本调研中的“引用”分三层：

1. **来源级**：页面知道由哪些文档生成。
2. **片段级**：页面知道由哪些 chunk 或段落支撑。
3. **主张级**：每个事实 Claim 都能定位到不可变 SourceVersion 中的 EvidenceSpan，并可独立计算覆盖、失效、冲突和替代状态。

FlyWiki 的目标是第 3 层；前两层只能评为部分具备。

## 1. nashsu/llm_wiki

调研快照：[`98786f6`](https://github.com/nashsu/llm_wiki/tree/98786f69684be5e85bc9beb5ada484b6d03edb88)（v0.6.6）。

### 已实现能力

1. **来源追溯与增量更新**
   README 明确说明每个生成页面把来源文件写入 `sources: []`，原始来源目录可自动监听外部新增、编辑和删除，摄取使用 SHA-256 缓存，队列支持持久化、崩溃恢复、失败重试和状态展示。来源重叠也被用作图谱关联信号。[README：摄取与来源追溯](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/README.md#L106-L152)

2. **真正的结构与语义 Lint**
   结构检查器确定性发现 orphan、no-outlinks 和 broken-link，并给出候选相关页/候选修复目标；语义检查器把页面摘要交给 LLM，要求输出 contradiction、stale、missing-page 和 suggestion。[结构检查源码](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/src/lib/lint-structural-core.ts#L115-L210) · [语义检查源码](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/src/lib/lint.ts#L198-L345)

3. **图谱健康洞察**
   Graph Insights 能识别 degree ≤ 1 的孤立页、低内聚社区和跨社区 bridge nodes；研究动作开始前有可编辑确认对话框。[README：Graph Insights](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/README.md#L176-L193) · [实现源码](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/src/lib/graph-insights.ts)

4. **重复检测、Review 与可操作修复**
   Maintenance 工具会扫描可能重复的实体/概念，要求用户逐组确认后才合并，合并进入串行队列；Lint 可以改写断链、补相关链接或创建 placeholder；异步 Review 让矛盾、重复和缺页保持待处理状态。[重复维护界面](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/src/components/settings/sections/maintenance-section.tsx#L256-L315) · [Lint 修复实现](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/src/lib/lint-fixes.ts#L1-L100) · [README：Review](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/README.md#L276-L284)

5. **删除后的结构清理**
   删除来源会清理摘要、索引和死 wikilink；多来源实体/概念页只移除被删来源而不直接删除整页。[README：cascade cleanup](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/README.md#L334-L346)

### 不足与适用借鉴

- `sources[]` 是**页面级**溯源；没有发现逐句/逐 Claim 的 EvidenceSpan、覆盖率、locator 校验或 `SUPPORTS/CONTRADICTS/UPDATES` 关系。
- semantic lint 只读取每页 frontmatter + 前 500 字预览，再由 LLM 判断，源码还专门过滤 LLM 误报的 missing-page；因此它适合做候选问题生成，不宜直接作为可信发布门禁。[语义检查上下文和误报过滤](https://github.com/nashsu/llm_wiki/blob/98786f69684be5e85bc9beb5ada484b6d03edb88/src/lib/lint.ts#L231-L286)
- 未发现外部 URL 定期可达性、撤稿/修订识别和不可变 Release 健康状态。
- 最值得 FlyWiki 借鉴：**Lint/Review/Graph Insights 三个入口的产品组织、问题卡片到一键修复的交互、重复合并的人审门槛**。

## 2. Tencent/WeKnora

调研快照：[`5780aff`](https://github.com/Tencent/WeKnora/tree/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a)。

### 已实现能力

1. **服务端 Wiki Lint 与 HealthScore**
   `WikiLintService` 定义并实际扫描 `orphan_page`、`broken_link`、`stale_ref`、`missing_cross_ref`、`empty_content`；报告含严重级别、问题数组、统计和 0–100 `HealthScore`。其中 `stale_ref` 指向已不存在/软删除的 knowledge，而不是泛化的网页过期。[Wiki Lint 源码](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/application/service/wiki_lint.go#L14-L343)

   源码也声明了 `duplicate_slug` 类型，但本次检查的 `RunLint` 中未看到生成该问题的分支，不能据枚举把“重复检测”算作 Lint 已完整覆盖。

2. **AutoFix 是真实后端行为**
   AutoFix 会把断裂 wikilink 降为纯文本、归档内容过少页面、剥离指向已删除 knowledge 的 source ref；如果该页已无其他来源，会删除页面，最后重建链接。[AutoFix 源码](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/application/service/wiki_lint.go#L348-L430)

3. **页面级 Chunk 引用与撤回链路**
   `WikiPage` 同时保存文档级 `SourceRefs` 和 chunk 级 `ChunkRefs`。摄取管线先识别候选实体/概念，再把来源 chunks 分类到 slug；系统记录 `UncitedSlugs` 供观测，但无引用的 slug 仍可保留 Description/Details fallback，因此这不是硬性引用覆盖门禁。[WikiPage 引用字段](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/types/wiki_page.go#L207-L224) · [Chunk citation 管线](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/application/service/wiki_ingest_cite.go) · [无引用 fallback](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/application/service/wiki_ingest_cite.go#L442-L467)

   文档重新解析时，旧 slug 与新提取结果会对账：已不存在的关联进入 `retractStale`，仍存在的实体/概念用“先撤旧贡献、再加新贡献”的替换语义；删除知识也有持久化 retract 任务。[重解析/撤回对账](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/application/service/wiki_ingest_batch.go#L1488-L1550) · [撤回任务](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/application/service/wiki_ingest.go#L555-L615)

4. **冲突候选与人工 Issue**
   页面合并提示要求所有新增事实直接受 source chunks 支持；清晰冲突优先更新并写入“Contradictions / Updates”，含糊冲突不覆盖旧内容。Agent 工具可把 `mixed_entities`、`contradictory_facts`、`out_of_date` 等问题保存为 `WikiPageIssue`，供后续处理。[页面合并规则](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/agent/prompts_wiki.go#L312-L397) · [Issue 工具](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/agent/tools/wiki_flag_issue.go#L15-L127) · [Issue 数据模型](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/types/wiki_page.go#L692-L728)

5. **运行健康和积压可观测**
   Wiki 统计包含 `PendingTasks`、`PendingIssues`、`IsActive`、孤立页数和最近更新；README 还列出文档解析 Trace、队列深度、模型并发治理、失败任务检查和手工重试。Wiki 摄取完成后才把 draft pages 转为 published。[WikiStats](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/types/wiki_page.go#L692-L705) · [运行队列与可观测性](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/README.md#L152-L154) · [草稿发布](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/internal/application/service/wiki_ingest.go#L2142-L2160)

6. **版本与人机协作入口**
   页面保存 immutable revision，回退本身也可再次回退；Wiki Browser 展示待处理 Issue，可忽略、逐项修复或启动 AI Auto-Fix 会话。[Revision API/说明](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/frontend/src/api/wiki/index.ts#L199-L256) · [Issue UI](https://github.com/Tencent/WeKnora/blob/5780affdfc76342ddd0f5cf95b548a1a4d0b2a5a/frontend/src/views/knowledge/wiki/WikiBrowser.vue#L389-L457)

### 不足与适用借鉴

- Chunk refs 归属于**整页**，不是一个独立 Claim 的 EvidenceSpan；页面正文还会主动去掉内联 chunk ID。因此无法直接计算“每条事实主张是否有证据”。
- Lint 的 broken link 是 Wiki slug，stale ref 是已删除 knowledge；没有发现网页 404、引用原文漂移、PDF bbox/页码 locator 失效等检查。
- 冲突处理主要位于生成提示和人工 Issue，不是全库 Claim 规范化、立场对齐与结构化冲突状态机。
- `HealthScore` 把孤立率、断链数、空页数压成单一分数，未纳入引用覆盖、冲突、来源新鲜度和发布状态；FlyWiki 已决定不使用一个模糊总分，应复用问题清单和维度指标，而不是照搬该分数。
- AutoFix 可能删除页面，虽有 page revision 能力，但未见 FlyWiki 所需的统一预览、KnowledgeChangeSet、跨对象原子回滚和发布审批。
- 最值得 FlyWiki 借鉴：**服务端 Lint API、问题数据结构、PendingTasks/PendingIssues/IsActive、解析 Trace/失败重试界面、页面版本与 Issue 修复入口**。

## 3. eugeniughelbur/obsidian-second-brain

调研快照：[`e6687ea`](https://github.com/eugeniughelbur/obsidian-second-brain/tree/e6687ea2fdfcca8a2f06fc82568c7933fc226180)。

### 已实现能力与模板边界

1. **`vault_health.py` 是真实检查器，不只是提示词**
   它确定性检查重复笔记、孤立笔记、过期任务、缺 frontmatter、空文件夹、wanted notes/缺失附件、未填模板，以及可选语义索引覆盖率；输出机器可读 JSON 和严重级别。[vault health 源码](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/scripts/vault_health.py#L818-L861)

2. **Freshness policy 有可执行 lint**
   规则要求每个事实必须是 timeless、dated snapshot 或 pointer。`freshness_lint.py` 检查未标日期的快事实、超过窗口的时间戳、无法解析的 typed pointer，并明确规定老化事实只做 re-observe、convert 或 retire，不静默删除。[Freshness policy](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/references/freshness-policy.md) · [Freshness lint](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/scripts/freshness_lint.py)

3. **断链、图关系与索引健康有真实代码**
   `heal_links.py` 只自动应用确定 stem/alias/faithful slug 匹配，模糊或歧义匹配进入 triage；`link_graph.py --lint` 检查 unknown type、dangling target、self edge、缺 inverse 及不对称关系循环；`vault_health.py` 会检查 `.obsidian-semantic-index.json` 对笔记的覆盖率并提示重建。[安全断链修复](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/scripts/heal_links.py) · [typed-edge lint](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/scripts/link_graph.py#L349-L394) · [索引覆盖检查](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/scripts/vault_health.py#L583-L618)

4. **引用规范有插件检查，但不是引用覆盖审计**
   AI-first rules 要求外部事实附 URL、日期与置信级别；Obsidian 插件会发现“已经带 URL 的行却没有 as-of 日期”。它不会把正文拆成事实 Claims，也无法发现一句外部事实完全没有 URL 的情况。[AI-first rules](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/references/ai-first-rules.md#L35-L75) · [插件 lint](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/integrations/obsidian-plugin/src/lint.ts#L24-L134)

5. **语义矛盾仍主要是 Agent 工作流模板**
   `/obsidian-health` 要求分派“Contradictions agent”，`/obsidian-reconcile` 要求 Agents 扫描 Claims/Entity/Decision/source freshness，比较新旧和权威性后改写或创建 open conflict。`vault_health.py` 本身的检查列表并不含正文 Claim 矛盾检测；typed-edge contradiction 只是在关系元数据层发现 A、B 互相以同一非对称关系指向的逻辑环。因此“语义冲突主张”应标为仅工作流模板。[健康命令](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/commands/obsidian-health.md#L10-L38) · [矛盾协调命令](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/commands/obsidian-reconcile.md) · [实际 health checks 列表](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/scripts/vault_health.py#L818-L841)

6. **修复风险分级值得直接借鉴**
   健康命令规定：缺 frontmatter、确定断链等安全修复可以提议自动执行；归档、合并、解决矛盾等破坏性修复必须列出并显式确认。AI-first rules 进一步要求：基于外部来源修改已有笔记只能形成 proposal，需用户确认。[健康修复分级](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/commands/obsidian-health.md#L29-L38) · [外部来源写入边界](https://github.com/eugeniughelbur/obsidian-second-brain/blob/e6687ea2fdfcca8a2f06fc82568c7933fc226180/references/ai-first-rules.md#L110-L145)

### 不足与适用借鉴

- 它主要操作 Markdown vault，没有中心数据库、Workspace 隔离、运行任务服务、不可变知识发布或 Claim/Evidence 实体。
- 来源 URL 通常只保存在 Markdown 行或 frontmatter，未形成不可变 SourceVersion/EvidenceSpan；也没有自动验证 URL 当前是否仍支持原主张。
- 多数跨页语义判断和修改依赖运行时 Agent 能否完整搜索、正确比较并遵循模板，不能作为强一致发布门禁。
- 最值得 FlyWiki 借鉴：**freshness policy、每条外部事实的日期标记、确定性修复与歧义修复分流、破坏性变更显式确认、wanted notes 作为知识缺口而非错误**。

### 对 FlyWiki 的边界结论

OpenKB 原生负责“**Wiki 编译产物自身是否结构合理、语义上是否存在候选问题**”；FlyWiki 的 `openkb-evidence` 扩展应负责“**知识是否有可验证证据、证据是否仍有效、哪些 Claim 冲突或被替代、某个 Release 是否可以可信发布**”。

因此建议复用而不是重做：

- 直接调用 OpenKB structural lint 与 semantic lint，并把它们的报告标准化为 FlyWiki `KnowledgeHealthFinding`。
- 断链修复仍由 OpenKB 执行，但必须包装成 FlyWiki `KnowledgeChangeSet`，保留预览、审计与回滚信息。
- FlyWiki 新增独立检查器：Claim 引用覆盖率、EvidenceSpan locator 有效性、SourceVersion 新鲜度/撤稿状态、Claim 冲突/替代状态、Release 完整性、共享知识库引用权限。
- OpenKB 的语义 lint 结果只能创建“候选问题”，不能单独阻断或批准可信发布；可信发布门禁应以确定性证据规则为主，人工确认处理语义歧义。

## 对一期“知识健康中心”的具体建议

参考上述项目后，一期能力建议收口为以下五层：

1. **OpenKB 原生检查层**：断链、孤立、缺 Wiki 条目、索引同步、frontmatter/OKF、语义候选问题。
2. **Evidence 扩展检查层**：Claim 覆盖、EvidenceSpan 定位有效性、SourceVersion 可访问性与新鲜度、冲突/替代状态。
3. **运行健康层**：OpenKB 编译、Celery 队列、失败重试、最后成功 Release、待审积压；产品交互可参考 WeKnora。
4. **知识结构层**：重复/孤立/稀疏社区、wanted concepts、跨域 bridge nodes；交互可参考 llm_wiki。
5. **治理层**：安全修复可批量执行，认知变更、证据解绑、合并、删除和发布必须确认；所有修改产生可回滚 `KnowledgeChangeSet`，参考 obsidian-second-brain 的风险分级但用服务端机制保证。

最终不建议显示一个模糊的“87 分可信度”。主界面应显示可解释的维度及问题数量，例如：引用覆盖、引用有效、来源新鲜、冲突待审、结构健康、编译健康、发布健康，并让用户从每个问题进入证据和修复动作。
