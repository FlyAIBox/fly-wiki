## 一、执行摘要

**产品定义**：一个 API-first 的「自进化知识库平台」（self-evolving knowledge base）。它不只保存用户收藏的截图、链接与资讯，而是持续完成“代读与初步理解 → 更新用户的主题认知 → 标记信息的可信度和相关性 → 在输出时提供可直接引用的证据链”，最终形成一份自我进化、可审计、可导出的活知识库（living wiki），并主动产出周报、主题动态和矛盾检测等洞察。

**一句话定位**：*你只管随手一存，知识自己生长。*

**面向核心场景的价值主张**：*收藏后即使没时间看，系统也会持续帮你理解和更新认知；需要写作、分析或决策时，直接找到可信、强相关、可追溯的证据。*

**核心结论**：**技术路线值得进入 Phase 0，但用户价值和市场差异尚未被证明。** Karpathy LLM Wiki 及多个开源实现支持“持久 Wiki + 来源追踪”的工程方向，移动端主动分享也符合平台权限模型；与此同时，Recall、Fabric、Khoj、Obsidian Second Brain 等已经覆盖自动组织、知识图谱、语义搜索或主动综合，不能再以“整合和洞察无人占位”作为立项依据。真正需要验证的候选差异是：**用户确认的认知版本 + 面向具体主张的证据关系 + 输出后的认知回写闭环**。建议只立项 Concierge 历史输出回放和封闭验证，达到 Gate 后再决定是否开发完整客户端。

| 评估维度 | 结论 |
|---|---|
| 市场需求 | ⚠️ 痛点合理但未验证（需要真实输出任务、重复使用和付费行为） |
| 市场时机 | ✅ 良好（Limitless 退场、Karpathy 模式引爆心智、端侧模型成熟、国内无 Glean） |
| 技术可行性 | ⚠️ 有条件可行（组件均有开源验证，自进化与证据排序的组合质量需 Phase 0 验证） |
| 商业可行性 | ⚠️ 模型存在但未验证（需订金、四周复用和单位成本数据） |
| 合规风险 | ✅ 可控（随手存模式规避采集合规问题；微信/爬虫红线明确不碰） |
| 竞争风险 | ⚠️ 高（竞品已覆盖整合、图谱和主动综合；更窄差异尚待真实操作验证） |

## 二、产品定义与演进过程

### 2.1 构想演进（三轮迭代）

| 版本 | 内容 | 关键取舍 |
|---|---|---|
| 初始 | PC+APP 五功能：文件整理、截图/剪贴板整理、洞察、自媒体拉取、IM 汇总 | 识别出本质是"收集→记忆→洞察"一条流水线 |
| 修订一 | 收集侧简化：用户随手存（截图/链接）+ 订阅来源 | 砍掉录屏/文件监控/IM 逆向，工程量 -60%，隐私包袱大减；代价是进入收藏工具红海 |
| 修订二 | 平台化：引擎 Day 1 即 API/Skill/MCP 化 | 个人 App、研究工作台、企业控制台成为同一引擎的三个客户端 |

### 2.2 核心用户任务：从“收藏负债”到“可信认知资产”

核心问题不是用户缺少收藏工具，而是收藏之后没有完成从信息到认知、再从认知到输出的转化：

1. **存了但没时间看、没空整理**：内容只增加收藏数量，没有形成主题结构，更不会更新用户已有认知；
2. **看过或让模型快速理解过，但状态不清楚**：搜索时无法区分“仅收藏”“机器摘要”“本人读过”“已交叉验证”，相似结果很多，却不知道哪些值得相信和采用；
3. **输出时重新寻找证据**：写文章、报告或做决策时，需要再次打开原文、定位段落、核对时间和出处，证据链拼装耗时且容易遗漏反例。

对应的核心 JTBD：

> 当我持续收藏大量可能有用的信息、却没有时间逐条阅读整理时，我希望系统替我完成初步理解并维护主题认知；当我要输出观点或做决策时，它能优先返回可信且强相关的内容，并给出可核验、可引用的完整证据链。

产品需要把每条内容从“一个收藏条目”转化为具有明确状态的认知资产：

| 状态 | 含义 | 产品行为 |
|---|---|---|
| 已收藏 | 仅完成原文/快照保存，用户和模型均未判断其质量 | 进入收件箱，不直接作为高置信结论 |
| 已机器处理 | 已完成解析、摘要、实体和观点提取 | 可检索，但明确标记为机器理解 |
| 用户已读 | 用户读过正文或关键段落并产生高亮/批注 | 提高个性化相关权重，不等同于事实已验证 |
| 已验证 | 有权威一手来源、多个独立来源互证，或经用户确认 | 可进入“可信证据”候选集 |
| 有争议 | 存在来源冲突、反例或适用条件差异 | 并列展示观点，不自动合并为单一事实 |
| 已过期 | 时效性内容被新信息替代或超过适用时间 | 默认降权，但保留版本和 supersession chain |

这里的“可信”不能由模型给出一个黑箱总分。系统应至少分开展示：**来源权威性、证据直接性、交叉验证程度、时效性、与当前问题的相关性、用户确认状态**。相关性高不等于可信，来源可信也不等于与当前问题强相关。

### 2.3 最终产品架构

```
收集入口（轻量，无系统权限）
  ├─ 手机 App：Share Sheet / 相册选图(OCR) / 粘贴链接
  ├─ 浏览器扩展：一键剪藏（存正文快照而非裸链接）
  ├─ PC 轻客户端：拖拽 / 全局快捷键
  └─ 订阅来源：RSS/RSSHub、newsletter 邮箱、微信文章分享入库
        ↓  原始层（不可变 Event：原图、快照、原文 —— 防失效、可审计）
  解析管线：OCR → 内容类型识别 → 摘要 → embedding
        ↓
  ★ 自进化引擎：新信息整合进主题笔记，重写调和矛盾，持续更新认知
        ↓  Wiki 层（markdown，全量可导出，Obsidian 兼容）
  ★ 证据引擎：认知状态 + 来源质量 + 直接性 + 交叉验证 + 时效性 + 查询相关性
        ↓
  输出层：可信检索 │ 证据包 │ 语义问答(带引用) │ 周报/主题动态/矛盾检测 │ 深度研究报告
```

理论基础：Karpathy LLM Wiki 三层架构（raw sources 不可变 / wiki 由 AI 拥有并重写 / rules 定义摄入更新查询规则），社区扩展（引用链、置信度、supersession chain）解决"重写式信息退化"问题。

搜索一个主题或准备输出时，不只返回相似内容列表，而是生成一个“认知与证据工作台”：

- 当前认知：系统基于哪些来源形成了什么结论；
- 可信证据：可直接支持结论的一手来源、原文摘录和定位；
- 补充材料：相关但证据强度较弱的背景信息；
- 反例与冲突：哪些来源持不同观点，分歧源自时间、样本还是立场；
- 认知变化：新信息修改或推翻了哪些旧结论；
- 证据缺口：哪些结论目前只有单一来源、二手转述或模型推断；
- 一键证据包：按引用格式导出观点、摘录、出处、时间、链接/文件位置和适用边界。

### 2.4 Day 1 API 面（自家 App 也只走公开 API）

```
POST /ingest        万物收集 → 归一化为不可变 Event
POST /consolidate   触发整合：Event 合并进主题笔记（同步/异步/批量）
GET  /wiki/*        主题页、引用链、修订历史
POST /query         语义问答（带引用溯源）
POST /evidence      围绕问题生成证据包（支持/反对/缺口/原文定位）
POST /insight       周报、主题动态、矛盾检测、趋势
GET  /export        全量 markdown 导出（信任基石）
Webhooks            整合完成 / 主题页更新 / 矛盾发现
```

配套生态：MCP server（接入 Claude/Cursor 等一切 Agent）+ Claude Skill 包（对标 obsidian-second-brain 的 44 命令模式，作为最早分发渠道）。多租户与命名空间 Day 1 进 schema。

## 三、市场分析

### 3.1 需求真实性

- 「收藏后没有消化、输出时重新寻找证据」是明确的问题假设，但当前还缺少本产品目标用户的任务回放、行为数据和付费证据。**需求假设不是“更好的收藏”，而是“将收藏持续转化为可信、可复用、可追溯的认知资产”。**
- Karpathy LLM Wiki 和 Obsidian Second Brain 证明“持久 Wiki、自动综合与定时维护”有开发者关注和工程实现；Recall、Fabric 等则说明普通用户已经可以使用自动组织、知识图谱和跨资料问答。**尚未验证的空缺是用户认知版本与证据化输出闭环，不是普通用户版 AI 知识库本身。**
- 研究场景：Elicit/SciSpace/Consensus 等工具的公认缺口是"无跨项目机构记忆，每次综述从零开始"——多个第三方评测独立指出。
- 企业场景：市场分界线已从"部署模式"移到"搜索工具止步于搜索，还是延伸到 AI 对话、深度研究和基于企业数据的 agent"。

### 3.2 市场时机（为什么是现在）

1. **Rewind/Limitless 被 Meta 收购并于 2025-12 下线录屏功能**，"个人记忆"市场留下真空；开源替代 screenpipe 偏开发者向、无移动端、无中文生态。
2. **端侧模型成熟**：小尺寸模型（Qwen 系列等）+ 系统 OCR 已可在消费级硬件完成预处理，成本结构成立。
3. **国内企业侧无 Glean**：Glean 年约 $5-6 万起步、需 100+ 席位；开源 Onyx 无中文优化、无飞书/钉钉连接器——50-500 人中国企业是无人服务的空档。
4. **Agent 生态分发红利**：MCP/Skill 已成为标准接入形态，为 API 产品提供近零成本的分发渠道。

### 3.3 目标用户分层

| 阶段 | 用户 | 付费意愿 |
|---|---|---|
| Phase 0-1 | 开发者/效率极客（经 Skill/MCP 触达） | 低（换取整合质量反馈与口碑） |
| Phase 1-2 | 知识工作者、内容从业者 | 中（订阅 ¥128-198/年） |
| Phase 3 | 研究生、分析师、咨询师 | 高（研究版加价包） |
| Phase 4 | 50-500 人中国企业 | 最高（席位 + 私有化） |

## 四、竞争格局

### 4.1 直接竞品：「收藏 + AI」赛道

| 产品 | 定价 | AI 深度 | 弱点（本产品的机会） |
|---|---|---|---|
| Cubox（中文标杆） | ¥98/年 | 快读总结、全库语义问答、微信收藏/OCR | 止步查询层：知识不生长、无主动洞察，存 1000 篇还是 1000 篇 |
| mymind | $79-129/年 | 自动打标/OCR/摘要 | 无导出无 API，只存不炼 |
| Recall | $10/月起（年付） | 自动摘要、组织、连接、知识图谱、全库聊天、MCP/API | 尚未验证是否区分用户认知版本和主张级证据关系 |
| Fabric | 订阅 | 多来源摄取、语义搜索、关系映射、AI 助手与会议内容 | 尚未验证是否提供用户认知对照与输出后回写闭环 |
| Mem 2.0 | $12/月 | 自动组织+语义召回 | 无 Android，导出弱，偏笔记 |

**关键判断（经首次证据回放修订）**：现有产品已经覆盖摘要、自动组织、知识图谱、查询和部分主动综合，不能宣称这些层“无人占位”。FlyWiki 的候选差异是：**Belief（用户确认认知）作为独立版本对象、Claim—Evidence 主张级关系、以及输出结果回写认知的闭环**。这只是待验证假设；官网未展示某能力不能作为竞品没有该能力的证据。

### 4.2 API 化后的相邻赛道：Agent 记忆层

| 玩家 | 架构 | 实力 | 与本产品的区隔 |
|---|---|---|---|
| Mem0 | 向量+LLM 抽取 | $24M 融资、AWS Agent SDK 独家、Q3'25 1.86 亿次 API 调用 | 记 Agent 会话中的事实碎片 |
| Zep | 时序知识图谱 | LongMemEval 63.8% | 记实体/事实的时间线 |
| Letta | 有状态 Agent 运行时 | 记忆自管理、可审计 | 服务单 Agent 行为 |

**区隔与策略**：三家记的都是"对话记忆"、服务 Agent 运行时；本产品做的是"文档/截图/文章/数据整合成的人类可读知识资产"，服务人和组织的认知。**不与 Mem0 拼会话记忆，但兼容其生态形态（MCP、宽松 SDK）借道分发。**

## 五、技术可行性

### 5.1 结论：有条件可行

所有外围组件（OCR、解析、检索、研究 agent、权限模型）均有成熟开源实现可参考或复用，无需攻坚。**核心未验证项是自进化与证据判断的组合质量**：LLM 将新信息整合进已有主题笔记时能否做到不失真、矛盾调和正确、溯源完整；检索时能否把语义相似与证据可信分开判断。社区已发现"重复重写导致信息退化"（wiki 版模型坍塌）的风险，对策为：

- 收集与整合分离：原始 Event 永久不可变，整合可重放、可回滚；
- 每条 Wiki 陈述携带指向原始 Event 的引用链 + 置信度 + supersession chain；
- 每个证据评分拆成可解释维度，禁止用单一“AI 可信分”代替来源核验；
- 检索采用两阶段排序：先召回强相关候选，再按来源、直接性、互证、时效和用户状态重排；
- 整合批处理（夜间）+ 端侧小模型做分类/OCR/embedding、云端大模型只做整合与洞察，控制成本。

### 5.2 技术栈建议

- 后端：云端为主（随手存模式下隐私压力小），SQLite/PG + 向量索引起步；
- 客户端：浏览器扩展 + 网页端优先，移动端 Share Sheet 为主入口（iOS 合规路径天然成立），PC 客户端 Tauri 延后；
- LLM：端侧小模型（预处理）+ 云端大模型（整合/洞察）分层。

### 5.3 平台约束（已通过随手存模式规避）

iOS 无后台常驻/剪贴板监听限制、Android ROM 后台查杀、微信无个人消息 API——在随手存模式下均不构成阻塞。

## 六、商业可行性

### 6.1 收入模型（三级火箭）

| 线 | 形态 | 定价锚 |
|---|---|---|
| 个人订阅 | 免费额度 + Pro（云端洞察、无限整合、跨端同步） | ¥128-198/年（介于 Cubox ¥98 与 mymind $79 之间） |
| 开发者 API | 按收集 Event 数 + 整合次数计费 | 行情参考：Mem0 Pro $249/月、Zep Flex $125/月 |
| 企业版 | 席位 + 私有化部署 + GenBI | ¥50-100/人/月，100 人以下即可起售（Glean 够不着的空档） |

可选 open-core 模式（核心引擎开源获客+信任，云服务和企业功能收费）——screenpipe、Onyx、Khoj 均验证此路径。

### 6.2 成本结构要点

- 最大变动成本是整合的 LLM token：以批处理 + 模型分层控制；参考 GPT-Researcher 单次深度研究 ~$0.005 的量级，单用户月度推理成本可控在订阅价的小两位数百分比内（需 Phase 0 实测）。
- Day 1 API 化增加 3-4 周工程投入（认证/限流/版本化/多租户/文档），换取 Phase 4 免重构——判定为值得。

### 6.3 留存逻辑（数据飞轮）

用户积累的 Wiki 迁移成本极高 → 订阅留存根基。随手存模式下飞轮依赖用户习惯（Cubox 留存难的根源），两个 Day 1 对策：
1. **快回报**：第一周即产出"你存的东西在生长"的周报；
2. **被动兜底**：订阅来源在用户不存入时仍让主题页持续生长，回访必有新内容。

## 七、风险与合规

| 风险 | 等级 | 对策 |
|---|---|---|
| 自进化/证据引擎质量不达标 | **致命** | Phase 0 硬关口：整合准确率、可信证据 Precision@5、引用链完整率不达标则不进入 Phase 1 |
| 巨头平台化（Apple Intelligence、腾讯 Marvis 等） | 高 | 跨平台+跨数据源+用户拥有数据（全量导出）；系统厂商不会聚合竞对平台数据 |
| 收藏赛道红海、差异化被模仿 | 中 | 自进化引擎的质量与数据飞轮是时间壁垒；API 生态先发 |
| 随手存习惯难养成 | 中 | 快回报周报 + 订阅来源被动积累（见 6.3） |
| LLM 成本失控 | 中 | 模型分层 + 夜间批处理 + 按量计费转嫁重度用户 |
| 平台化分散火力 | 中 | 纪律：Phase 0-2 期间 API 唯一大客户是自家 App；生态只做 MCP + 一个 Claude Skill 包 |
| 合规红线 | 低（已规避） | 微信个人消息 API 不碰；自媒体只做用户主动分享导入、不做后台爬取；企业 IM 走飞书/钉钉/企微官方开放平台 |

## 八、实施路线图

| 阶段 | 时间 | 交付 | 验证关口（Gate） |
|---|---|---|---|
| **Phase 0** 引擎即产品 | 第 1-2 月 | 自进化引擎 + 证据引擎（API+CLI+MCP+Claude Skill，无 GUI），以 100-300 条真实收藏构造 20 个检索/输出任务 | 整合准确率、可信证据 Precision@5、引用链完整率、证据准备耗时达标；不达标不前进 |
| **Phase 1** 个人 MVP | 第 3-5 月 | 浏览器扩展+网页端+手机 App（Share Sheet）；认知状态、可信检索和一键证据包；全走公开 API | 次周留存 >40%；证据准备耗时相对原流程下降 >60%；出现自然付费意愿 |
| **Phase 2** 生长闭环+生态 | 第 5-8 月 | 订阅来源自动整合、Obsidian 同步、个人付费上线、Connector SDK+Webhook | 跨端用户留存/转化显著高于单端（验证"归仓"价值） |
| **Phase 3** 研究工作台 | 第 8-13 月 | 文献 Connector（Semantic Scholar/arXiv）+ 深度研究报告（外部文献+自有 Wiki 联合检索），`POST /research` API 化 | 研究用户付费转化；报告质量对标 Elicit |
| **Phase 4** 企业版 | 第 13-20 月 | 飞书/钉钉/企微 Connector、ACL 权限镜像、私有化部署、GenBI（Vanna+WrenAI 模式） | 首批 50-500 人企业签约；因多租户/引用链/API Day 1 已备，本期为"加装"而非"重构" |

## 九、关键成功指标（KSF/KPI）

1. **整合准确率**（Phase 0 核心）：抽样审计重写后信息保真度、矛盾调和正确率、引用链完整率；
2. **可信证据 Precision@5**：针对真实输出任务，前 5 条结果中被用户判定为“可信且可直接支持/反驳当前论点”的比例；
3. **Time to Evidence**：用户从提出问题到获得可引用证据包的时间，相对原流程的降幅；
4. **认知更新率**：收藏内容中，最终新增、强化、修正或推翻主题认知的比例；
5. **证据复用率**：已入库证据在后续文章、报告、问答或决策中被再次引用的比例；
6. **生长率**：存入内容被整合进主题页并在洞察中被引用的比例（对标竞品的"打开率"死穴）；
7. **次周/次月留存** 与 **跨端用户占比**；
8. **API 生态信号**：第三方 MCP/Skill 调用量、Connector 社区贡献数；
9. **单用户推理成本 / ARPU 比**（毛利健康度）。

## 十、结论与建议

1. **建议只立项 Phase 0 产品发现，不建议直接立项完整客户端**。技术方向有开源实现支持，但用户价值、竞品差异、重复使用和付费仍缺少一手证据。
2. **核心赌注是“自进化 + 可信证据”的组合质量**——不仅要能整理，还要让用户在真实输出任务中更快找到可信、强相关、可核验的依据；将 Phase 0 设为硬性投资关口，不达标即止损或转向。
3. **坚持三条纪律**：API-first 但范围克制（7 端点）；Phase 0-2 生态只做 MCP+Skill；合规红线（微信/爬虫）绝不触碰。
4. **差异化定位一以贯之**：对个人——"你只管随手一存，知识自己生长"；对开发者——"Mem0 让 Agent 记住用户说过什么，我们让人和企业拥有可审计的自进化知识资产"；对企业——"每个结论可点开看到原始依据的团队第二大脑"。
